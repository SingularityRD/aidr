# Continuing on another machine

Everything in this repository is committed. This file describes what is **not**
in the repository and exactly how to recreate it, so a fresh clone is a working
checkout rather than a broken one.

`docs/evidence/` holds the small, irreplaceable records — live run results, gate
verdicts, and the reasoning behind each finding. The large derived artifacts
(bundles, container images, test transcripts) are deliberately not tracked; they
are regenerated by the commands below.

---

## What you need installed

| Tool | Version this was verified with | Notes |
|---|---|---|
| Node.js | 24.12.0 | The repo pins `pnpm@10.29.3` via `packageManager` |
| pnpm | 10.29.3 | Provisioned through corepack; do not use a different major for the offline install gate |
| Docker | Desktop 29.4.3 | Needed for the local control plane |
| Python | 3.13.12 | Only for the AIG bridge tests |
| Git + GNU tar | Git for Windows ships tar | Reproducible archives require GNU tar, not the BSD one |

Two IDE hosts are needed only for the extension E2E suites: Cursor and VS Code,
installed normally. Set `AIDR_CURSOR_PATH` and `AIDR_VSCODE_PATH` if they are not
in the default locations.

**The `.release-evidence/` directory is gitignored and was 4.1 GB.** The parts
worth keeping were copied into `docs/evidence/`; everything else is regenerated.

## Recreating the local control plane

The installation directory is derived, so it is not tracked. Recreate it:

```powershell
# 1. Prepare an isolated loopback installation.
node scripts/deployment-prepare.mjs --development `
  --output .release-evidence/aidr-local-deployment-r9 `
  --supabase-url http://127.0.0.1:8000 `
  --dashboard-url http://127.0.0.1:8080 `
  --upstream-dir deploy/upstream `
  --region self-hosted --tenant-region self-hosted

# 2. Start it. The API gateway publishes on 8000 and the dashboard on 8080.
$d = ".release-evidence/aidr-local-deployment-r9"
docker compose --project-directory $d --env-file "$d/.env" -f "$d/compose.yml" up -d

# 3. Apply the canonical migrations.
node scripts/deployment-migrate.mjs $d
```

**The port must be 8000.** `deployment-prepare` always publishes the gateway on
`127.0.0.1:8000`, but it writes whatever `--supabase-url` it is given into
`deployment.json` and `.env`. Passing the Supabase CLI's default 54321 produces an
installation that points every client at a port nothing is listening on, and the
resulting failure looks like a broken service rather than a misconfiguration.

Confirm it is up:

```powershell
curl -H "apikey: $((Get-Content $d/.env | Select-String '^ANON_KEY=') -replace '^ANON_KEY=','')" `
  http://127.0.0.1:8000/auth/v1/health
```

Expected: HTTP 200 with a GoTrue version string. The startup also needs port 8080
free; a leftover stack from an earlier run will hold it, so remove stale
containers first if the dashboard container fails to bind.

## Running the full rehearsal

One command performs the whole sequence, in the only order that terminates:

```powershell
node scripts/run-evidence-gates.mjs
```

It settles the tree, rebuilds the release candidate, rebinds the claim records,
runs every gate sequentially, and prints the verdict. It writes the evidence
index but does **not** commit it — committing it moves HEAD and invalidates the
commit stamps inside it. The reasoning, and the three ordering constraints it
encodes, are in `docs/production-readiness/evidence-index-regeneration.md`.

Optional environment for a fuller run:

```powershell
$env:AIDR_AIG_PYTHON      = "$PWD/.release-evidence/aig-bridge-venv/Scripts/python.exe"
$env:AIDR_E2E_ENABLE_IDE_HOST = "1"
$env:AIDR_CURSOR_PATH     = "$env:LOCALAPPDATA/Programs/cursor/Cursor.exe"
$env:AIDR_VSCODE_PATH     = "$env:LOCALAPPDATA/Programs/Microsoft VS Code/Code.exe"
$env:DASHBOARD_SMOKE_BASE_URL = "http://127.0.0.1:8080"
$env:AIDR_CODEX_CREDENTIALS   = "$env:USERPROFILE/.codex/auth.json"
```

Each is optional. A gate whose prerequisites are absent reports itself blocked,
which is the honest outcome and is preserved rather than worked around.

**The AIG bridge venv is not tracked.** Recreate it with the bridge's own
requirements before expecting gate 15 or the `aig-bridge-contract` E2E suite to
pass; the system Python lacks `tenacity` and collection fails.

## The two gates that do not pass

Both are blocked on things outside the repository, and neither should be forced:

**`18-native-host`** requires a named QA owner, endpoint owner and support owner
to sign an acceptance record for a specific candidate. The gate's own README says
the best a local run can reach is `LOCAL_SCENARIOS_COMPLETE_REVIEW_OPEN`. There is
no way to write those names that is not a fabrication. Details, including why the
seven-case scenario mechanism is wired for fixture hosts rather than the six real
ones, are in `docs/evidence/native-host-status-20260916.md`.

**`19-release-e2e`** requires provider credentials for the `claude`, `opencode`
and `openclaw` suites, plus live-service receipts and a deployed dashboard. Seven
suites do pass — 60 assertions — including the live model-interception suite.
State per suite is in `docs/evidence/gate19-release-e2e-status.md`.

## The one habit worth keeping

Several defects found in this work were **gates reporting the wrong thing** rather
than the product misbehaving: a Vitest report claiming `success: true` while
running zero tests, a determinism gate that could never pass, two guards
disagreeing about which files were derived. When a gate fails, check that it is
measuring what it claims to measure before trusting either the pass or the fail.
