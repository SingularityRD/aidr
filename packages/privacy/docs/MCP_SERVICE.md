# Installed MCP gateway with private text scanning

This optional single-tenant, text-only profile connects the released gateway package to the actual private mTLS scanner. Install the institution-delivered `@singularity/aidr-privacy` artifact and the matching signed `@singularityrd/aidr-mcp-gateway@0.6.0`; the latter is an optional exact peer. It is required when using `aidr-privacy-mcp`, while the standalone text service does not require it. The signed public library entry verifies its gateway artifact with the operator's verifier configuration. Use the commercial delivered build and pinned release signer configuration; a development build or test signer is not production acceptance.

Start the approved private text service first. Provision the real certificate-bound user/device/provider bundle through the configured institution broker and store it in the existing OS vault. The MCP service uses that exact tenant/session; it does not invent a second identity authority or derive privacy permission from the gateway bearer token.

Keep `examples/platform/client-config.mjs` and `mcp-config.mjs` inside the installed package under `/opt/aidr-private/node_modules/@singularity/aidr-privacy` so bare package imports and their adjacent modules resolve. Copy only completed reference JSON into administrator-owned `/etc` directories. Set `AIDR_PRIVACY_CLIENT_CONFIG` and `AIDR_PRIVACY_MCP_CONFIG` to their absolute JSON paths. Fill `mcp-config.example.json` with the actual signed tool manifest, trusted signer PEM, institution tenant, bounded allowlist, exact public upstream addresses and SHA256 of the actual gateway client token. Its `gatewayTokenRefs` load isolated upstream/client probe tokens from the existing core OS vault into the gateway's established environment-based credential interface. The host needs the institution-delivered core package and its actual runtime dependencies for this configuration sample. No token is printed or embedded in JSON. The [portable handoff](../deployment/PRIVATE_INSTALL.md) prepares these references.

Run `aidr-privacy-mcp --config /opt/aidr-private/node_modules/@singularity/aidr-privacy/examples/platform/mcp-config.mjs` under a dedicated service UID. It resolves the installed gateway package, never a repository source path. Startup rejects mixed tenant configuration, caps complete JSON at 256 KiB, forces `routingRequired:true` and requires an actual byte-identical allow from the mTLS `/v1/protect` endpoint before constructing the listener. Missing/revoked credentials, unavailable policy/model, changed output or a missing supported signed gateway package refuse startup. The gateway's own startup then requires its isolated upstream credential, fixed DNS pins and actual 401/403 negative probes without a credential and with every gateway client credential. Missing pins, shared credentials, accepted negative probes and unexpected DNS answers refuse readiness. No caller-configured scanner/transport override is exposed by the private launcher.

Keep the gateway's existing operator approval workflow: review the actual quarantined connection binding and signed tool definitions with `aidr-mcp-approve`, then approve that exact binding. The launcher does not approve a toolset. It preserves the gateway's base scanner, input schema/attestation, session checks and policy/toolset checks after asynchronous work.

Both input/output callbacks call the real private `/v1/protect` endpoint over mTLS, bind all supplied request/session/tenant/toolset metadata and verify the original payload digest. Only `allow` with byte-identical JSON releases the original gateway message; redact/review/block and scanner failure deny it. Opaque image/audio/resource payloads remain denied because this text profile never reports `opaqueInspected:true`. Modern `2026-07-28` is opt-in and requires stateless transport with proper protocol/capability metadata. Legacy paths reconstruct their forwarded envelopes and may omit unsupported caller metadata rather than forwarding it.

Deploy `deployment/mcp-text-service.nft.example` instead of the text-only template for the same UIDs. It supplies three distinct process identities: application can reach only local text/MCP listeners; MCP service can reach only the local private scanner, approved resolvers and pinned MCP upstream; text service can reach only the approved IdP/broker/provider destinations. The application receives only gateway credentials and cannot read service vaults, upstream credentials, approval state or configuration. The packaged `aidr-privacy-mcp.service.example` requires the text service and existing firewall unit; install the approved combined rules at that unit's configured rules-file path before enabling both services. Set the institution OS-vault session environment for each dedicated service identity. Validate effective rules and make a direct upstream request under the actual application UID: it must fail while an approved gateway call succeeds. This template is not installed or certified on the current/customer host. Gateway credential probes cannot prove host firewall isolation or prevent a privileged administrator changing rules.

`npm run test:integration:mcp` is the explicit installed-profile regression. It fails if the supported installed gateway is absent or its artifact signature is invalid; it never silently skips. The fixture runs an actual public gateway HTTP listener, actual private scanner mTLS listener and actual controlled HTTPS upstream with signed test identities and operator approval. Only DNS/transport is controlled for the upstream; synthetic signatures and the controlled sink do not establish public provider connectivity, institution authority or effective host routing. It exercises clean release, modern metadata PII denial before upstream, PII output withholding after execution and durable privacy-session revocation before the next call. The production launcher has no such transport overrides. Final deployment acceptance must repeat on the actual signed delivery, issuer/broker/vault, upstream and firewall.

Repository CI and RC use `test:ci:platform` to enforce the complete private Node suite, that installed-profile regression and the Python NER installer/corpus/artifact security units. Node aggregate results must contain tests and show every test passed, with no failures, cancellations, skips or TODOs; a successful process exit alone cannot pass the gate. Python units run with `-I -S` and reject empty, skipped or expected-failure results, using only the standard library. This development gate builds only fresh scratch private output/assets, and uses the existing gateway fixture builder with ephemeral keys and isolated verifier HOME. It requires Linux/Node≥22.16, OpenSSL/libseccomp2 and absolute physical `AIDR_PYTHON`/`AIDR_TEST_PYTHON` paths with the pinned parser dependencies. It does not download models, approve a model, copy model/corpus staging directories or alter production signing trust. This CI orchestration script is repository tooling, not a customer runtime requirement.
