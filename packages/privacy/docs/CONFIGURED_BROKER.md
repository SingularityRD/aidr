# Configured private text route

This is an installable, explicitly selected application route. The packaged `ConfiguredSessionBroker`, `TextGatewayClient`, `aidr-privacy-service` and `aidr-privacy-send` connect the existing mTLS privacy gate to OIDC and an institution's authoritative device/provider-account broker. No new public release package, automatic main hook interception or OpenAI-compatible endpoint is introduced.

Install the verified private package alongside the existing released core package and, for the SDK host example, the SDK. Use the packaged `examples/platform/service-config.mjs` and its reference-only JSON; `client-config.mjs` reuses the same core OS credential vault. `file-acl`, an unavailable vault, missing referenced secrets and a vault for another platform fail. Server provider credentials, TLS private keys, independent data/audit keys and OIDC client secrets live in vault entries; paths and reference IDs live in administrator-owned JSON. On Linux the institution must supply the service account's accessible Secret Service/DBus session. The example supervisor does not create a keyring daemon or accept plaintext fallback.

Populate the actual signed tenant policy/public keys, certificates, tenant, roles, model and vault references. Encryption/audit vault entries are canonical Base64 for exactly 32 random bytes; TLS key entries are PEM. Do not use sample data or share data and audit keys. Set `AIDR_PRIVACY_CONFIG` to the absolute service JSON path; launch the existing service with the absolute packaged configuration module. All module imports/configuration are trusted deployment code. Protect and sign them with the private delivery archive/image. The `REPLACE_` values deliberately prevent a successful deployment.

## Supported identity contract

The administrator pins two HTTPS issuers and their certificate roots. Discovery requires the exact configured issuer and same-origin discovery/JWKS/token/authorization endpoints. Keys come only from the fixed issuer's HTTPS JWKS at startup; token `jku`/`x5u` never select keys. RS256 with RSA ≥2048 bits and Ed25519/EdDSA are supported. This narrow integration rejects cross-origin endpoints, unsupported algorithms, malformed/duplicate/private JWKS keys, redirect responses, compressed bodies and oversized responses. It is not a claim of arbitrary IdP compatibility or OpenID conformance certification. Restart with approved keys after issuer key rotation; unknown key IDs fail closed. Corporate private DNS/IP issuers are explicit administrator endpoints with pinned CA and normal hostname verification. Provider egress retains its separate public-address/DNS/TLS checks.

OIDC authorization-code login uses the confidential client's `client_secret_basic`, PKCE S256, nonce and one-use state. Pending state lives encrypted in the existing durable transient namespace for at most five minutes and is bound to the actual enrolled mTLS certificate. The configured registered HTTPS redirect belongs to the host application; its existing authenticated callback forwards `state` and `code` to `client.session('complete', {state, code})`. The packaged session CLI accepts that JSON on stdin for operator use. No browser-local bearer storage or public callback server is added. The IdP ID token is verified locally against issuer, client audience, signature, lifetime and nonce, and sent to the authoritative broker over a separate mutually authenticated service channel.

The institution must deploy the following broker endpoints under its configured issuer. This is the implemented wire contract, **not** an included MDM database, Intune/Jamf connector or manufactured enterprise-account acceptance:

| Broker POST path | Request | Required behavior |
|---|---|---|
| `/v1/sessions/bootstrap` | `destination`, `certificateThumbprint` | Authenticate the service's mTLS identity; issue a real configured service principal and its device/provider grants, or deny startup. |
| `/v1/sessions` | `idToken`, `destination`, `certificateThumbprint` | Independently verify the IdP token and query authoritative enrollment/compliance and provider-account ownership for this user and certificate. Deny missing evidence. |
| `/v1/sessions/refresh` | Existing user/device/provider tokens, destination, certificate thumbprint | Recheck identity, actual device compliance/account status and grant validity; issue a fresh bundle for the same subject/session/device at exactly the next session version. |
| `/v1/sessions/revoke` | Existing user/device/provider tokens | Revoke the external broker session. Local durable revocation happens before this call, including when the remote call fails. |

Grant replies are JSON with exactly `userToken`, `deviceToken`, `providerToken`. All are separate JWTs signed by the configured broker issuer, with the configured audience, `token_use` of `user`/`device`/`provider`, strict `sub`, `jti`, `tenant_id`, `sid`, `session_version`, `iat`, `exp` and lifetime ≤600 seconds. Initial versions are 1. User grants contain authoritative group IDs and, for an OIDC-created session, `oidc_iss` and `oidc_sub` matching the verified ID token. Device/provider grants share `device_id`; device grants require real `managed:true`, `compliant:true`, and `cnf:{"x5t#S256":"<SHA256 of DER client certificate, base64url>"}`. Provider grants require the exact selected origin, `account:"enterprise"`, `verified:true`, `logged_in:true`, and authorized scope IDs. Local code verifies these assertions; the approved issuer remains responsible for their truth.

Local session records are atomically provisioned only after every grant validates. Refresh requires a live mTLS-bound context, repeats the context check after the network wait, advances the durable version and invalidates all older credentials. Failed refresh, including an invalid MDM grant, invalidates the captured old lease; it cannot invalidate a concurrently refreshed newer version. Expired/revoked sessions cannot be revived or reset to version 1; a new login must get a new session ID. Concurrent refreshes have one winner. Bad/missing initial claims cannot provision a session. Revoke requires the remote broker's explicit `revoked: true` acknowledgement, while local revocation remains effective even if that acknowledgement fails. Credentials expire even when no explicit revocation reaches the service; continuous MDM push/revocation webhook is not supplied. Refresh before expiry and after device/account changes; a client must authenticate again after an unknown/failed refresh and must never fall back to an unverified bundle.

The bootstrap is service readiness evidence, not user login. Broker/MDM and IdP credentials, supported issuer behavior and live organization approval remain required customer deployment inputs. No live customer provider call, real IdP login or enterprise-account acceptance occurred in the repository tests.

## Host connection

Use `client.session('begin')` to obtain the authorization URL; complete the registered host callback over the same enrolled certificate. `examples/platform/session-cli.mjs` stores successful login/refresh bundles in the existing OS vault. Set `AIDR_PRIVACY_CLIENT_CONFIG` to the absolute client reference-only JSON. The CLI accepts `begin`, `complete`, `refresh`, `revoke`; `complete` reads `{state,code}` JSON from stdin. Tokens are never printed.

The host's final provider function is `TextGatewayClient.send(text)`. The `sdk-final-send.mjs` example combines the existing SDK generic action middleware with this explicit final model-send seam. Existing SDK tool verdicts remain their own boundary. Remove direct provider clients and provider credentials from this host process; its network boundary must permit only the private gateway. The supplied stdin send CLI calls that same seam, returns a bounded dispatch receipt and exits unsuccessfully for blocked/review/unknown/withheld output. It performs no automatic retry. A null output must never return the original prompt. Unknown outcomes may already have reached the provider.

## Mandatory host/network boundary

The firewall is part of this deployment profile. Copy and fill `deployment/text-service.nft.example` with distinct fixed service/application UIDs, approved resolver IPs and the actual IdP/broker/provider IPv4 addresses. The application UID can contact only the local gateway at TCP8443. The service UID can contact only those approved identity/provider HTTPS addresses and DNS resolvers, and reply to the loopback gateway client; every other IPv4/IPv6 destination for those UIDs is rejected. No wildcard HTTPS, direct-provider application route, proxy/redirect fallback, arbitrary telemetry or IPv6 escape is authorized. Deploy separate host/network policy for a remote application; do not expose the sample loopback rule to a whole subnet. An IP allowlist is not an assertion that a shared cloud IP belongs exclusively to one provider; the fixed application transport still verifies its configured hostname and TLS.

The packaged systemd examples require the firewall unit before the text service starts and leave the output rules active after shutdown. Validate with `nft --check`, inspect the effective rules, stop/drain the application during rollout, and test a denied direct-provider connection under its actual UID before accepting traffic. DNS/provider address changes require an approved atomic firewall update; fail closed when stale. Integrate with the institution's current firewall manager and ingress policy without flushing the global ruleset. Monitor for privileged changes to the table; `RemainAfterExit` does not detect an administrator removing rules later. Local root/host administrators can override host policy, and other UIDs are outside this narrow profile. The firewall template has not been installed on this user's host or certified on a customer's system. Relevant primary references: [nftables manual](https://netfilter.org/projects/nftables/manpage.html), [systemd execution restrictions](https://github.com/systemd/systemd/blob/main/man/systemd.exec.xml).

## Actual verification and remaining acceptance

The concrete [data/document/audio operations](DATA_OPERATIONS.md) connect administrator labels and source ACLs to the final gate, provide the existing Linux Office/PDF text reconstruction route, and expose optional complete PCM audio removal. These are explicit opt-in operations; ASR/video acceptance remains absent.

The real HTTPS regression uses enrolled certificates, HTTPS issuer discovery/JWKS, a synthetic signed OIDC/MDM broker and an actual durable runtime. It proves PKCE/state/nonce, certificate replay rejection, version refresh/revoke, final request/reply masking and a blocked classified request making no outbound sink call. The synthetic issuer/control sink establishes code/transport behavior, not MDM truth, provider account approval or learned-model accuracy. OIDC references: [OpenID Connect Discovery](https://openid.net/specs/openid-connect-discovery-1_0-final.html), [OAuth security BCP](https://www.rfc-editor.org/info/rfc9700/).

Run acceptance on the signed delivered private artifact with actual customer issuers, MDM/provider evidence, registered callback, vault, network policy and approved NER digest. Independent TR/EN PERSON/ADDRESS qualification remains separate; a downloaded model or capability declaration never substitutes for the customer corpus. Final provider dispatch stays bounded text-only; optional data/document/audio operations have their own stated limits. No ASR/video quality or universal egress guarantee is claimed.
