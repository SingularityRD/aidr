# AIDR inline MCP gateway

This loopback HTTP gateway evaluates MCP tool-call arguments **before** upstream execution and inspects tool results, and opted-in resource and prompt content, **before** they reach a model. It requires a high-entropy bearer token for every request, a tenant-specific explicit tool allowlist, an Ed25519 signed manifest with an operator-approved toolset, and live upstream tool-list agreement. Upstream connections use the core pinned-DNS transport with redirect, private-address and decoded-byte rejection. Text results are fully buffered and scanned by pattern-based rules (see [Output inspection limits](#output-inspection-limits)); findings, unsupported output, drift, malformed/oversized streams and unavailable checks yield only a generic JSON-RPC error.

Client-specific `allowedServerMethods` permits inspected server requests and notifications on the originating request's SSE stream. Requests use opaque, single-use gateway IDs bound to the authenticated tenant, client, server, session and active parent request. Replies pass the same scanner and policy boundary before the gateway restores the upstream ID. Upstream `initialize` advertises only the `sampling`, `elicitation` and `roots` client capabilities that the client both advertised and opted into. A server message the client did not opt into follows the operator `serverInitiated` policy for its category (`sampling`, `elicitation`, `roots`, `notifications`): `deny` (the default) refuses the request, and `ignore` drops the message without delivering it and records a category-only `server_initiated_method_ignored` coverage event. Methods outside those categories, and a server request sent in place of a JSON response body, are always refused. Denied methods and content that cannot be fully inspected yield a machine-readable `error.data` (`type: "mcp_gateway_refusal"`, with a category-only `serverMethod` for server methods) and a redacted `aidr.mcp_gateway.coverage` event through the optional `onEvent` dependency. The CLI emits audit and coverage events on stderr.

Startup emits one typed direct-upstream coverage event per configured server. Without an injected `directUpstreamCheck`, host routing remains explicitly `unobservable`; an observer may report `routed`, `unobservable`, or `bypass`, and a detected bypass refuses startup. The mandatory routing option below separately verifies credential isolation and endpoint pins; it does not change host firewall policy.

Every `tools/call` is normalised to `mcp__<serverId>__<toolName>` and evaluated by the core `evaluateToolCall` pipeline (threat rules, allowlist, policy, the server's optional tenant `dlpPolicy`, and the optional `agentProfiles` document — see `docs/agent-profiles.md`; a client may be bound to one profile with `"profile"`) before it is forwarded. A profile deny returns `profile_denied`. `deny` returns `arguments_blocked` (or `input_not_fully_inspected` when the arguments exceed the core inspection limits, which is always a deny), `ask` returns `approval_required` (a block pending out-of-band operator action; there is no agent-callable approval), and missing rules or an evaluator failure return `detection_unavailable`. `error.data` (`type: "mcp_gateway_decision"`) carries only the reason code, verdict category and, for built-in rules, the threat ID. Session-level layers (runaway guardrails, toxic-flow chains; a runaway pause is `approval_required` with category `agent_runaway`) keep one record per MCP conversation, never per client credential: per bound `Mcp-Session-Id` (stored as a digest), or, for a `stateless` server, per client, server and gateway process. A stdio bridge runs its own gateway, so that is one MCP connection; on a shared HTTP gateway a client's stateless calls to one server share a record until restart, so issue one client token per agent. Nothing carries over into another gateway process. Refusals the gateway decides before evaluation (`tool_not_allowed`, `arguments_schema_mismatch`) keep their own codes, and a pre-execution `approval_required` stops the call before upstream execution, so no output refusal can follow it. The bundle embeds the repository threat and trusted-domain rules and writes them to `<stateDir>/detection-rules/<sha256>/` on first use; `detection.threatsDir`, `detection.allowlistsDir` and `detection.agentConfigPath` (absolute paths) override them.

Every observed tool list is also scanned for tool poisoning (the `mcp_tool_metadata` rules in `threats/context-poisoning.yaml`): hidden Unicode, orders to read local secrets or agent configuration first, cross-tool shadowing and injected directives in tool names, descriptions and input schemas. A blocking finding refuses every request to that server with `tool_metadata_poisoned` (`error.data.category: "mcp_tool_poisoning"` and the rule ID), even for a signed, operator-approved toolset; review-level findings are emitted as `tool_metadata_suspicious` audit events. When the rules cannot be loaded, requests fail closed with `detection_unavailable`. The tool description is passed to the argument evaluator, so memory and vector-store write tools are recognised by their description as well as their name and their arguments are scanned for memory poisoning. See `docs/poisoning-protection.md`.

Binary tool output (`image`, `audio`, embedded resource blobs) must first pass bounded inspection: an allowlisted, byte-verified MIME type (`binaryOutput.allowedMimeTypes`, default PNG/JPEG/GIF/WebP), canonical base64 within `binaryOutput.maxDecodedBytes` (default 256 KiB), and a scan of the printable runs inside the bytes; text-like resource blobs are decoded as UTF-8 and scanned. Without an `outputGuard`, output that passes these checks is delivered with a `binary_output_bounded_inspection` coverage event (`coverageStatus: "limited"`, since pixel and audio semantics are not interpreted). When an `outputGuard` is configured, including the text-only guard the standalone gateway and stdio binaries install, that opaque content is additionally released only if the guard attests `opaqueInspected: true`; otherwise it is refused with `output_uninspectable`. See `docs/platform-guides/mcp-gateway.md`.

Build after building core, then start the self-contained bundle:

```sh
pnpm --filter @singularityrd/aidr-core build
pnpm --filter @singularityrd/aidr-mcp-gateway build
node packages/mcp-gateway/dist/aidr-mcp-gateway.mjs /secure/path/gateway.json
```

The gateway listens on `127.0.0.1` only. Point the MCP client's server URL at `http://127.0.0.1:7789/mcp/<serverId>` and send `Authorization: Bearer <token>` on every request. A remote client needs an operator-managed TLS/mTLS reverse proxy that preserves the authorization header and does not expose a bypass route to the upstream server. Configure the client to use only this URL; a host that can still call the original MCP server directly is outside the gateway's enforcement boundary.

Every request, including `GET /healthz`, must carry a `Host` header naming the bound port on a loopback name (`127.0.0.1:<port>`, `localhost:<port>` or `[::1]:<port>`), or an exact `host:port` listed in the optional top-level `allowedHosts` array (for an operator reverse proxy); anything else gets HTTP 421 `host_forbidden`. This defends against DNS rebinding in addition to the `Origin` refusal and the bearer token. Request bodies must be uncompressed UTF-8 JSON: a `Content-Encoding` other than `identity` is refused with HTTP 415 `unsupported_content_encoding`, a non-UTF-8 `charset` with 415 `unsupported_charset`, bytes that are not UTF-8 (for example UTF-16) with 400 `invalid_request_encoding`, and unparseable JSON with 400 `invalid_rpc_request`.

For an MCP client that launches a stdio command, configure its command to run the bundled bridge instead:

```sh
export AIDR_MCP_CLIENT_TOKEN='<random bearer token whose SHA-256 is in gateway.json>'
node packages/mcp-gateway/dist/aidr-mcp-stdio.mjs /secure/path/gateway.json tenant-a client-a server-a AIDR_MCP_CLIENT_TOKEN
```

Pass the token through the process environment, never as a command argument. The bridge binds that token to the exact tenant, client and server in the protected gateway configuration, starts an ephemeral loopback gateway, and emits inspected JSON-RPC messages on stdout. It keeps reading correlated client replies while upstream tool requests wait. It accepts newline-delimited UTF-8 JSON-RPC input up to `maxBodyBytes` per frame. A rejected notification, unexpected reply or malformed transport shuts down the bridge; stderr carries no raw tool data or token. Each client process needs its own bridge instance. Protect the environment and configuration from other local users.

**stdio mode limits.** The MCP client launches the bridge as the agent's own user, so the gateway configuration, the client token, any `upstreamAuthEnv` credential and the attestation state directory are all readable (and usually writable) by that user. stdio mode is therefore a convenience mode: it inspects the traffic that flows through it, but it is **not** a credential-isolation or approval boundary, and an agent that wants to can read the upstream credential and call the upstream directly or edit `gateway.json`. Every bridge start prints a fixed warning saying so on stderr, plus a second warning when the bound server has `upstreamAuthEnv`. Set the top-level `"stdioUpstreamCredentials": "refuse"` (default `"warn"`) to make a bound server with `upstreamAuthEnv` refuse startup with `stdio_isolation_refused:stdio_upstream_credential_refused`; that setting is only meaningful when the configuration file itself is not writable by the agent's user. For the isolation guarantees described under required routing below, run the HTTP gateway as an operator-owned service and point clients at its URL.

Example configuration shape (replace every placeholder and keep the file private):

```json
{
  "stateDir": "/var/lib/aidr/mcp-attestation",
  "approvalKeys": { "ops-key-1": "<operator approval Ed25519 public key PEM from aidr-mcp-approve --generate-key>" },
  "port": 7789,
  "maxBodyBytes": 262144,
  "clients": [{
    "id": "client-a",
    "tenantId": "tenant-a",
    "tokenSha256": "<64 lowercase hex SHA-256 of a random 32+ character token>",
    "allowedTools": { "server-a": ["search"] },
    "allowedServerMethods": { "server-a": ["sampling/createMessage", "elicitation/create", "roots/list", "notifications/progress"] }
  }],
  "servers": [{
    "tenantId": "tenant-a",
    "id": "server-a",
    "url": "https://mcp.example.com/mcp",
    "transport": "json",
    "sessionMode": "stateless",
    "protocolVersions": ["2025-11-25"],
    "signedManifest": { "key_id": "publisher-key", "manifest": {}, "signature_b64": "..." },
    "trustedSigners": { "publisher-key": "<Ed25519 public key PEM>" },
    "revokedKeyIds": []
  }]
}
```

`transport` can be `json` or `sse` and selects Accept preference; both upstream media types are accepted. SSE uses fatal UTF-8 decoding, complete-event framing, total byte and event limits, and a 15-second request timeout. Permitted control messages are scanned before delivery; tool output remains withheld until its correlated final result passes validation. The connection is cancelled after that final result, without waiting for SSE EOF. Unknown IDs, duplicate IDs in an active upstream session, replayed replies, malformed envelopes and nonempty HTTP 202 acknowledgements are rejected. At most 16 tool requests per tenant and 256 pending server replies (64 per tenant) are admitted; replies remain admitted when tool slots are occupied.

For an upstream bearer token, set `upstreamAuthEnv` to an environment variable name; do not put the secret in the config or URL. `sessionMode: "required"` binds upstream `Mcp-Session-Id` to the authenticated client, tenant and server in memory for 30 minutes. Restart invalidates sessions and pending exchanges. Changing an upstream credential invalidates pending exchanges. The gateway forwards `notifications/initialized` only after manifest attestation and session validation and requires a bodyless HTTP 202 upstream acknowledgement. Omit `allowedServerMethods` to refuse every server-initiated method. Supported entries are `sampling/createMessage`, `elicitation/create`, `roots/list`, `ping`, `notifications/progress`, `notifications/message`, and `notifications/tools/list_changed`; sampling, roots and elicitation also require the corresponding client capability. Elicitation form/URL modes are restricted to the modes the client advertised. The client must accept `text/event-stream` to receive server messages.

`protocolVersions` explicitly limits each upstream. Its default is `2025-03-26`, `2025-06-18`, and `2025-11-25`. To use the supported tools flow in [MCP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http), select `protocolVersions: ["2026-07-28"]` and `sessionMode: "stateless"`. Native clients send per-request `_meta` protocol version and capabilities; the bridge mirrors that version to HTTP. This mode supports `server/discover`, `ping`, `tools/list`, `tools/call`, the scoped resources/prompts methods (complete results only), complete results and [MRTR input requests](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr) for the approved sampling/elicitation/roots methods. There is no initialize handshake or independent server request in this mode. MRTR retries require a new JSON-RPC ID, identical original tool/arguments, the exact requested input-response keys, and the authenticated owner's single-use gateway continuation handle. Upstream opaque state is restored only after reply validation; handles expire after five minutes. Native client UI/consent remains the client's responsibility. This is a bounded tools implementation, not a claim that every method in the current MCP specification is supported.

For required routing, add `"routingRequired": true`, each server's `"upstreamAuthEnv": "AIDR_MCP_UPSTREAM_TOKEN"` and exact `"pinnedAddresses": ["<approved public IPv4/IPv6>"]`, and each client's `"probeTokenEnv": "AIDR_MCP_CLIENT_TOKEN"`. Start with `node .../aidr-mcp-gateway.mjs /secure/gateway.json --require-routing`, or append the same flag to the stdio command. The flag forces the requirement even if the config omits it. Startup requires the real matching client token in each probe environment variable, refuses shared gateway/upstream credentials, and probes the pinned upstream without credentials and with each gateway client credential. Only HTTP 401/403 proves this credential separation; accepted requests, redirects, server failures, missing credentials and DNS answers outside the configured pins refuse startup.

Deploy the gateway as an operator-owned service and provision the upstream credential only to that service. Fleet-managed client configuration must point exclusively at the gateway URL or its stdio command; ordinary client identities receive only gateway credentials and cannot read or modify the gateway environment, configuration, approval state or executable. Configure the organization's existing outbound proxy/egress policy to permit the gateway service to the exact approved upstream endpoint and to prevent client processes reaching that endpoint directly. Include a direct request from the actual client host/process identity in deployment acceptance: unauthenticated and gateway-token requests to the original endpoint must fail, while an approved tool call through the gateway succeeds. Re-run this check after endpoint, credentials or fleet-routing changes. The startup credential probes complement this network check; they cannot establish isolation for a client that already possesses another upstream credential. No global host firewall change is performed by this package.

The default scanner reads all text and JSON, but it is pattern-based (see [Output inspection limits](#output-inspection-limits)). Image/audio blocks and embedded resource blobs follow the bounded-inspection and guard rules above; resource links and other unrecognised tool output remain refused. Resource blobs and opaque prompt content follow the resources/prompts rules below. An embedding host can pass asynchronous `toolGuard` and `outputGuard` to `createMcpGateway`: each receives a bounded detached `payload` snapshot, `direction` (`to_upstream`/`to_client`), `method`, abort `signal`, `tenantId`, `clientId`, `serverId`, originating `requestId`, original tool `inputSha256`, `payloadSha256`, `runtime: "mcp-gateway"`, `sessionId` (or null), `protocolVersion`, and signed `toolsetHash`. Only `{ allowed: true, coverage: "full" }` permits release; opaque content additionally requires `opaqueInspected: true`. Missing/failed/partial guards deny. A private local scanner adapter must verify its own policy/session binding and scan the complete serialized snapshot; if it redacts or changes that text, it must deny release of the unchanged original. Text-only adapters must never claim opaque inspection. No private-service dependency or media decoder is bundled into this gateway.

### Signed manifest lifetime and rotation

Every configured `signedManifest` is verified when the gateway starts: schema, trusted and non-revoked signer, Ed25519 signature, validity window and lifetime. An invalid manifest refuses startup before the CLI prints `listening`, exits `1` with the precise reason (for example `startup_failed:manifest_expired`, `startup_failed:manifest_lifetime_too_long`, `startup_failed:manifest_invalid_signature`) and emits a `type: "mcp_gateway_manifest"` event with `status: "rejected"`. A manifest whose `expires_at - issued_at` exceeds the operator maximum is refused; set it with the top-level `"manifestPolicy": { "maxLifetimeDays": 7, "expiryWarningDays": 2 }` (shown with the defaults; `maxLifetimeDays` is a whole number from 1 to 90, `expiryWarningDays` from 0 to `maxLifetimeDays`). A manifest that will expire within `expiryWarningDays` produces a `status: "expiring"` event (`reasonCode: "manifest_expiring_soon"`, with `expiresAt`) at startup and at most hourly afterwards. A manifest that expires while the gateway runs is refused per request with the client-visible reason `manifest_rejected`; the audit event carries `manifestReason` (for example `expired`).

To rotate, have the publisher re-sign the manifest with a higher `sequence` and a new `expires_at`, then replace `signedManifest` (and, if needed, `trustedSigners` or `revokedKeyIds`) in `gateway.json`. The HTTP gateway CLI polls the file every two seconds and also reloads on `SIGHUP`: it adopts the change only when every manifest verifies and no other field changed, prints `AIDR MCP gateway reloaded <n> signed manifest(s)` and emits `status: "reloaded"` events; otherwise it prints `AIDR MCP gateway reload refused: <reason>` (for example `manifest_reload_failed:configuration_change_requires_restart`) and keeps the current configuration. A changed toolset or signer is quarantined for operator approval as usual. Library hosts call `gateway.reloadManifests(config)` themselves. Each stdio bridge reads the configuration once at launch.

On first contact or a signer, configured connection, or signed toolset change, the gateway quarantines the manifest. Review the publisher, configured endpoint and authentication identity, complete tool descriptions/schemas, requested tool allowlists, `toolsetHash`, and `bindingSha256` in the private quarantine state through an operator channel, then approve it with the operator approval key.

Every approval is an Ed25519 signature by an operator approval key. The gateway holds only the public half (`approvalKeys` in `gateway.json`, required, at most 16 entries); the private half is a passphrase-encrypted PKCS#8 file that the operator keeps outside the agent's reach (an operator-only account, removable media or a vault export) and unlocks only for an approval. Create it once, on the operator's machine:

```sh
node packages/mcp-gateway/dist/aidr-mcp-approve.mjs --generate-key /operator/aidr-approval-key.pem ops-key-1
```

The command asks twice for a passphrase of at least 12 characters (no echo; when stdin is not a terminal it reads the first line of stdin, never an argument or environment variable), refuses to overwrite an existing file, writes the key with mode `0600` and prints the `{"approvalKeys": {"ops-key-1": "<public key PEM>"}}` block to merge into `gateway.json`. Restart the gateway after changing `approvalKeys`. To approve a reviewed quarantine:

```sh
node packages/mcp-gateway/dist/aidr-mcp-approve.mjs --key /operator/aidr-approval-key.pem [--expires-in-days 90] /secure/path/gateway.json tenant-a server-a <toolsetHash> <bindingSha256> <operatorId> "approved ticket and reason"
```

The command refuses a key file readable by group or others, an unencrypted key, a wrong passphrase, and a key whose public half is not in `approvalKeys`. It derives the expected toolset, signer and connection binding from the signed manifest in the configuration (never from the state file), requires the operator's `toolsetHash` and `bindingSha256` to match them, checks that the quarantined tool list really hashes to that toolset, and records a signed entry over the server id, toolset, publisher key id and key hash, binding, operator, reason and validity window. The approval expires after `--expires-in-days` (default 90, at most 366); the toolset is quarantined again afterwards and needs a fresh approval. On every request the gateway honours only an entry whose signature verifies under a configured approval key and whose window is current; an unsigned, altered, unknown-key or expired entry is ignored and reported as an `approval_entry_ignored` audit event with an `approvalRejection` code (`unsigned_approval`, `untrusted_approval_key`, `invalid_approval_signature`, `approval_expired`, ...). A process that can write the state directory, including an agent running as the same user as a stdio bridge, therefore cannot approve a toolset unless it also holds the operator key and its passphrase.

Approval is deliberately not an MCP tool or HTTP endpoint. The command requires the exact `bindingSha256` the operator reviewed; if the connection changes before approval, the old value is refused. `stateDir` must be an absolute path (`config_invalid:statedir_must_be_absolute` otherwise). The gateway refuses to start (`startup_failed:state_dir_not_owned` or `startup_failed:state_dir_group_or_world_writable`; the stdio bridge stops with the same detail under `bridge_stopped`), the approval command refuses to approve, and attestation fails closed when the directory, or a tenant directory inside it, is not owned by the serving user or is group- or world-writable (POSIX mode bits; Windows ACLs are not inspected, restrict them yourself). A missing directory is created with mode `0700`. Each state file is sealed with an HMAC-SHA256 under a random key in `<tenant dir>/.state-integrity.key`; a file that was edited, unsealed or copied from another server fails closed (`manifest_rejected`). The seal key is readable by the serving account, so the seal catches tampering by anything that does not hold it; the operator signature is what stops a same-user process. State written by an earlier version has no seal and no signed approvals: remove the old `<stateDir>/<tenant hash>/<server hash>.json` files after stopping the gateway and approve each toolset again. Rotate/revoke signer keys, approval keys and client tokens through the private configuration and restart the gateway; removing a key from `approvalKeys` withdraws every approval it signed. No raw output or token is included in gateway errors or audit callback events. The signed manifest authenticates tool definitions; the operator approval binds the configured connection, not the upstream executable bytes or host routing. Attestation locks are never stolen automatically; after a lock timeout, stop every writer and verify none remains before removing only the matching `.lock` file, never the state JSON.

The four `dist/*.mjs` files bundle their own core, JavaScript dependencies and the repository threat and trusted-domain rules. Copy all four together with `aidr-artifact.manifest.json` and `aidr-artifact.manifest.sig`; Node.js 22.12+ is required, while pnpm and `node_modules` are not. Commercial binaries refuse startup when the signed set is incomplete or changed. The operator commands exit `2` on usage errors and `1` otherwise, printing only a fixed `<stage>[:<detail>]` reason code (for example `config_unreadable:enoent`, `standalone_profile_failed:standalone_privacy_unavailable` or `integrity_verification_failed:missing_signature`). The signer private key and client bearer tokens are never part of the bundle.

Trusted installed hosts can import `createMcpGateway` from `@singularityrd/aidr-mcp-gateway`. The package export resolves to `dist/aidr-mcp-library.mjs`, which verifies the same operator-trusted signed artifact before exposing its factory. Pass the parsed private configuration and approved guard dependencies to that factory and await `gateway.listen()`; use `gateway.close()` during shutdown. The library cannot approve a toolset. The gateway object has no `approve()` method, only the read-only `approvalTarget()`. The library, gateway and stdio bundles contain no code that signs or records an approval. That code lives only in `dist/aidr-mcp-approve.mjs`, which exports nothing and is not a package export (`src/__tests__/library-approval.test.mjs` checks the built bundles). So an agent that loads the library through an import path computed at run time, which the CLT-SELF-009 rule cannot see, still cannot approve its own quarantined toolset. Copying the signing code does not help either: the gateway honours only entries signed by a key in `approvalKeys`. A private launcher can inject its installed scanner adapter without adding a private-service dependency to this package. The three CLI assets remain the minimum required artifact set; selected scanner-host deployments must also install the signed library and their separately verified launcher.

Work admission is bounded to 64 parent requests globally and 16 per tenant; capacity rejections return HTTP 429 (`gateway_busy` when the global cap is reached, `tenant_busy` for a tenant over its share) and close the rejected connection. Each shared pool (parent requests 64, pending server replies 256, MRTR continuations 256) keeps its last quarter (16, 64, 64) as a reserve that is admitted only to a tenant holding fewer than its guaranteed floor (2, 8, 8 entries), so tenants running at quota fill at most the remaining three quarters and cannot starve a quiet tenant. The optional `tenantQuotas` object (`activeRequests`, `pendingReplies`, `continuations`) sets the per-tenant quota (defaults 16, 64, 64); a value below the guaranteed floor or above the global cap minus the reserve refuses startup. Client replies are admitted separately so active parents can complete. This provides callback headroom for cooperative clients, not guaranteed socket reservation: idle and partial connections also count toward the 100-socket ceiling. The existing operator proxy/fleet deployment must control connection flooding.

Before starting a commercial bundle, provision the independently delivered Ed25519 artifact-verification public key in the gateway host's `~/.singularity-aidr/config.json` under `integrity.public_keys_pem`, with `integrity.enabled` and `integrity.verify_on_start` set to `true`. `scripts/deployment-prepare.mjs --artifact-verification-public-key-file <public.pem>` validates the key and writes this block to `agent-config.json`; install or merge that generated configuration at the default path for the account that runs the gateway. The gateway's own `gateway.json` is a separate file and intentionally does not accept the artifact-verification key.

In the portable customer kit, run `node deploy/gateway/aidr-mcp-gateway.mjs /secure/aidr-mcp-gateway.json`. After an operator has reviewed the quarantined connection and toolset, run `node deploy/gateway/aidr-mcp-approve.mjs --key <operator approval key file> /secure/aidr-mcp-gateway.json <tenantId> <serverId> <toolsetHash> <bindingSha256> <operatorId> "approved ticket and reason"` (create the key once with `--generate-key`, as above). The approval command and its key are an operator action; neither must be exposed to an agent.

Supported scope is the explicitly versioned tools flow, the guarded resources/prompts passthrough below, and the approved bidirectional methods described above, over authenticated HTTP POST or its stdio bridge. Tool results may contain text, bounded binary (`image`, `audio`) and embedded `resource` content as described above, with optional structured JSON. `tools/list` pagination, independent GET/SSE streams, resource subscriptions, list-change notifications, completions, partial tool-result delivery, sampling tool execution and unconfigured methods remain refused. MCP clients that require those methods are not compatible yet. This package does not establish host-level egress control or proof of protection for every connector; deployment must test the exact MCP client and server pair and enforce direct-access isolation.

### Output inspection limits

Output inspection is pattern-based: the bundled scanner matches known prompt-injection phrasing, secrets and personal data. For every result it reads the serialized JSON, all string values (NFKC-normalised, zero-width characters removed), the text of consecutive content blocks, prompt messages and resource contents joined in order (with and without a separator, so a phrase or key split across two blocks is matched as one), and base64, base64url and hex runs that decode to readable text (two nested rounds). It does not understand meaning: paraphrased instructions without known trigger phrases, other encodings or ciphers, and text inside images or audio pass unless a rule matches. Treat it as a heuristic layer, not a guarantee. For semantic inspection, inject an `outputGuard` (for example an LLM-based classifier) as described above; the gateway releases a result only when both the scanner and that guard allow it.

### Resources and prompts

`resources/list`, `resources/templates/list`, `resources/read`, `prompts/list` and `prompts/get` are relayed only for a client that opts in per server. Add `"allowedResources": { "server-a": ["file:///docs/*", "https://intranet.example.com/handbook"] }` and/or `"allowedPrompts": { "server-a": ["summarize"] }` to the client entry; each key must also appear in `allowedTools`. A resource entry is either an exact URI or a literal prefix ending in a single `*` (end prefixes with `/` so `file:///docs*` does not also match `file:///docs-private/`). Requested and returned URIs must be printable ASCII with an explicit scheme; dot segments, backslashes and percent-encoded dots/separators are refused rather than normalized. Without an allowlist the method is refused before any upstream call, and initialize/`server/discover` advertise `resources`/`prompts` only to a scoped client whose upstream offers them; `subscribe` and `listChanged` are never advertised.

Each request is checked against that scope, rebuilt from its known fields (`cursor`, `uri`, `name`, string-valued `arguments`, and `_meta` in 2026-07-28 mode), and then passes the same `to_upstream` inspection as a tool call: the scanner over the complete JSON-RPC body and the configured `toolGuard`. The signed toolset is re-verified against the live upstream before every context request, so a drifted server is refused here as well. Responses are validated and minimized: list entries outside the client's scope are dropped, `nextCursor` and request `cursor` values are relayed unchanged, every `resources/read` content URI must be in scope, and resource contents must carry exactly one of `text` or canonical base64 `blob` with a `mimeType`. Prompt messages must be `user`/`assistant` with text, image, audio, embedded resource or resource-link content. The client-visible result then passes the scanner and `outputGuard` with `method` set to the MCP method. A `blob`, image/audio data, embedded resource or resource link is opaque: it is released only by an `outputGuard` that returns `opaqueInspected: true`, and is otherwise refused (`unsupported_binary_output` without a guard, `output_uninspectable` with a text-only guard such as the standalone binaries'). Resource and prompt list metadata is inspected but is not part of the signed tool manifest, so it has no signer attestation or drift baseline of its own.

A guard verdict may carry `decision`; anything other than `"allow"` (including `"ask"`) yields `policy_blocked`. An `ask` is a block pending out-of-band operator review: the response carries no action identifier and the gateway exposes no approval path to the agent. `resources/subscribe`, `resources/unsubscribe` and client-sent `notifications/resources/updated`, `notifications/resources/list_changed` and `notifications/prompts/list_changed` are refused with `resource_subscription_refused` and a redacted coverage event; the stdio bridge stops on any client notification other than `notifications/initialized`. Server-pushed resource or prompt notifications are server-initiated methods outside `allowedServerMethods` and are refused. Every allow and deny is reported through the same audit callback as tool calls.

The input guard runs on the complete forwarded JSON-RPC body, including per-request metadata. The output guard also covers client-visible initialization and tool-list responses. Internally generated correlation IDs use random UUIDs; they contain no timestamp or user data.

Run focused source tests without rebuilding shared core artifacts with `node packages/mcp-gateway/scripts/test-source.mjs` from the repository root. It bundles tests against current core source into a temporary directory, runs them, and removes the temporary files. Set `AIDR_MCP_TEST_PATTERN` to a Node test-name pattern to select a focused regression.

Tool input-schema regexes use a conservative ReDoS-resistant subset: `pattern` and `patternProperties` expressions are limited to 256 characters, reject groups, alternation and backreferences, and allow at most one quantifier. Regex-matched string values and property names are limited to 4096 UTF-16 code units. One validation call also shares a 1,000,000-unit aggregate budget, charging each regex attempt by pattern-source length times input length. Schemas or arguments outside these bounds fail closed before tool execution.
