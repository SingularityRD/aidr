# Tenant admission operators

Cloud payment does not automatically enable agent enrollment. A database administrator must separately authorize a named operator for one tenant, then that operator may invoke the service-only licensed-admission RPC after checking the approved contract, seat count, expiry and tenant owner. Customer owners and finance approvers cannot grant themselves admission. On-prem customers use the separately licensed bootstrap path.

The `public.admission_operators` table has no browser or service-role table grants. Provision it only through the controlled database-administrator change process, recording the change ticket and the administrator in the database access log. Set a finite expiry; if omitted, the database grants only 30 days. Review active rows at least weekly and remove or revoke unused access. Renew only after a fresh authorization review. The admission RPC rejects expired or revoked operators and any operator who is also a member of the target tenant.

For a paid cloud activation, independently verify the signed order or contract reference, exact tenant and owner IDs, purchased seats and finite license end date. Invoke `grant_licensed_tenant_admission` through the restricted `operator-admin` workflow ([operator-admin.md](operator-admin.md)), which additionally requires an allowlisted, AAL2-verified platform operator and records an actor-attributed audit receipt; never put the service-role key in a browser, customer script, ticket or log. For on-prem and air-gapped customers, prefer the signed-license import ([licensing](licensing.md#renewal-seat-changes-and-importing-a-signed-license)): a workspace admin stages the vendor-signed file, and you apply it from the Operator console or `operator-admin.mjs license-apply`; the seats and end date then come from the signed file instead of being typed, and the same admission-operator and non-member checks apply. Verify `get_tenant_admission` returns `licensed`/`active` for that tenant and the intended effective seat count. An invoice status or Stripe/Paddle webhook is evidence for finance, not an admission grant. To withdraw access, invoke `revoke_licensed_tenant_admission`; it advances the tenant's revocation epoch in the same transaction. A disconnected agent cannot learn a new revocation until it reconnects or receives the revocation feed, so do not promise instantaneous offline revocation.

Tenant offboarding immediately revokes operator and admission rows, then deletes them only after their respective retention windows and legal-hold checks. The database-administrator change log and application audit receipt should be included in the customer acceptance evidence.
