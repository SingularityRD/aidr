# COM-011 region and data-residency audit — 23 September 2026

**Decision: OPEN.** This is a source/configuration inventory, not a data-residency attestation or approval to process BMC data. The [COM-011 commercial receipt](./commercial-gate-receipts.json) remains open. Cloud and customer on-prem need separate, candidate-bound acceptance.

## What is actually known

At 18:40 UTC on 23 September 2026, the read-only Supabase CLI project list returned the repository-linked **`aidr-pilot-eu`** project as `ACTIVE_HEALTHY` in **`eu-central-1`**. This establishes the pilot project's primary region at that instant; it does **not** establish where every request executes, every log or backup is retained, or where data is transferred. No customer/production project, signed candidate, regional contract or regional negative test was inspected. The read-only check was `pnpm dlx supabase@2.117.0 projects list --output json`, filtered to the linked project ID in `supabase/.temp/linked-project.json`; no credential was printed.

The provider behavior matters here: [Cloudflare documents](https://developers.cloudflare.com/data-localization/how-to/workers/) that regional Worker execution requires Regional Services on a **custom domain**, that Workers code/secrets remain globally deployed, and that regionalization does not extend to outgoing subrequests. Its [compatibility matrix](https://developers.cloudflare.com/data-localization/compatibility/) marks `workers.dev` incompatible with Regional Services. [Supabase documents](https://supabase.com/docs/guides/platform/regions) that a project region locates **primary project data**, not regulatory compliance; [Edge Functions execute near the requester by default](https://supabase.com/docs/guides/functions/regional-invocation) unless a region is selected. These are provider descriptions, not proof of AIDR's live configuration.

## Candidate-bound acceptance required

1. Name the exact offered footprint: cloud region(s) or BMC on-prem; separate the Free pilot. Until a production cell is provisioned, do **not** claim EU/US/APAC placement or EU-only processing. The current repo provisions no such three-region service.
2. Bind the signed release digest to a per-cell inventory of Cloudflare hostname/account regional settings, Supabase project ID and specific region, Edge Function invocation region, Storage, Auth, logs/analytics, backups/replicas, SMTP, IdP, billing, Sentry and every configured integration. Record provider evidence and named Operations/Privacy owners without publishing credentials.
3. With **synthetic data**, exercise every enabled ingress (browser, endpoint, webhook and support/export), inspect actual response region headers and redacted provider logs, and run cross-region routing/tenant-access negative tests. Reject a regional claim if any mandatory path or its log/backup/transfer destination is unknown or outside the approved boundary.
4. Restore an authenticated backup on a separate approved host; verify backup region, retention/legal hold and deletion expiry. Complete the [COM-003 privacy handoff](./com-003-privacy-acceptance-2026-09-23.md) with DPA, subprocessors, transfers and customer responsibility split. Have Operations, Privacy/DPO and Legal sign the exact candidate and claim text in the COM-011 receipt.

**Current sale-safe statement:** “The linked internal pilot's Supabase primary project reports Frankfurt (`eu-central-1`). AIDR has not yet demonstrated or approved end-to-end data residency for a customer cloud or on-prem deployment.”
