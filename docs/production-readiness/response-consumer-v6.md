# Fleet response consumer v6: local implementation evidence

The control plane already exposes a tenant- and agent-bound `POST /v1/revocations` command transport. `poll` leases one command; `ack` records acceptance or rejection; `result` records the agent-reported outcome. The new `FleetResponseCommandConsumer` in `packages/core/src/response-command-consumer-v6.ts` follows that exact state sequence for one command at a time.

The consumer accepts only four typed commands (`agent_pause`, `agent_resume`, `network_isolate`, `network_release`), a valid enrollment identity, a scoped API key, and HTTPS (except explicit loopback development). It bounds and validates the response, checks expiry and any identity fields present, and rejects commands for which no installed adapter declares support. It never executes after an unconfirmed ACK. It reports success only after the adapter applies the action, independently observes the resulting state, and the server confirms the `succeeded` receipt. Transport ambiguity is returned as `outcome_unknown` rather than a fabricated success. No generic shell or arbitrary command executor exists.

`FleetResponseCommandWorker` in `packages/core/src/response-command-worker-v6.ts` adds a supervised polling loop and a required native adapter. Its two-slot, HMAC-authenticated journal stores tenant/agent identity, the enrolled installation identifier and API-key hash binding, the current command, a monotonic local sequence, and the last 256 completed command IDs. Each slot is written and synced before it becomes active; the raw API key remains only the in-memory MAC secret. A host-local exclusive lock prevents simultaneous worker cycles; a dead process lock can be recovered. A live lock, invalid journal, changed enrollment key or device binding, or identity mismatch halts action processing. `onCycle` exposes outcomes to service telemetry, and the loop throws on a journal failure so its supervisor can alert.

The durable phases are `polled` → confirmed ACK → `acknowledged` → persisted `execute_intent` → adapter execution and independent verification → persisted `result_pending` → confirmed server result. After restart, `polled` retries the idempotent ACK; `result_pending` retries only the result receipt. A restart at `execute_intent` **never replays the action**. It verifies the host state and leaves the outcome unknown when the state cannot be proven. An unsupported command persists rejection intent before sending a rejection ACK. The recent-ID cursor suppresses immediate duplicate delivery, but is deliberately bounded; the server remains authoritative for command ID uniqueness and terminal state.

An unresolved journal entry blocks polling the next command. This prevents a silent skip when the server's TTL or state transition makes a late ACK/result impossible, but requires operator reconciliation for a permanently uncertain outcome. The worker does not automatically clear such entries or claim that an expired server lease was successfully enforced.

This is a **transport and local recovery boundary**, not field acceptance for T13. The response consumer now sends an enrollment binding containing the installation identifier (`iid`) and SHA-256 API-key hash; the revocations function checks both against the agent-bound key before accepting poll/ack/result. This is not hardware, OS, or independently signed device attestation. The current response payload still omits an independently signed command and explicit signed tenant/agent identity fields. The repository does not yet install this worker as a persistent endpoint service or provide an OS adapter that can prove actual network isolation, host hook pause/resume, or third-party credential revocation. The one-shot consumer rejects commands with `unsupported_action` when no adapter exists; the durable worker requires an adapter and should not be started as a diagnostic poller. A reported command result remains agent-reported evidence, not OS/provider containment evidence. OS-specific journal ACL validation, key rotation recovery, abrupt power-loss testing, and a customer-installed single-instance supervisor remain open.

To close T13, bind the worker to each installed host runtime and service supervisor, implement and test allowlisted OS/provider adapters with independent state verification and rollback, add signed command/identity material to the control-plane payload, and run native-host and customer-network drills that show both the enforced effect and server receipt. Field evidence must include expiry, repeated delivery, revoked identity, offline endpoint, partial isolation, power loss, key rotation, and rollback outcomes.

Local verification covers the consumer's poll/ack/result binding, audit callback, restart states, replay suppression, journal corruption and enrollment mismatch, plus provider fail-closed and independent-verification paths. The attestation helper and Edge-handler ordering have focused tests. These are isolated local tests with simulated control-plane responses and adapters; they do not establish native-host or customer field acceptance.
