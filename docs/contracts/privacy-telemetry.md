# Contract: Browser Guard -> AIDR control plane privacy telemetry (fixed; both sides must follow exactly)

Transport: POST {controlPlaneBaseUrl}/functions/v1/ingest
Headers: Authorization: Bearer <Browser Guard ingest-only key (`aidr_ingest_...`, scope `ingest:browser_guard`; a tenant `aidr_live_...` key is still accepted)>, Content-Type: application/json
Credential: deploy an `ingest:browser_guard` key (dashboard API Keys -> "Browser Guard ingest-only key", owners/admins). Managed browser policy is readable by the profile's user (chrome://policy), so the key is treated as disclosed: /v1/ingest accepts it only with agent_runtime "browser_guard" and only privacy_scan and shadow_ai_usage events (anything else -> 403 api_key_scope_denied / event_type_not_permitted), budgets it per key (AIDR_BROWSER_KEY_INGEST_RL_PER_MIN, default 6000 events/min), registers at most its install_limit distinct iids (-> 403 install_limit_exceeded), never lets it take over an agent of another runtime (-> 403 agent_runtime_mismatch), and answers with a delivery acknowledgement only (no signed entitlement). Every other API-key endpoint refuses it (403 api_key_scope_denied).
Body envelope (same envelope other connectors use):
{
  "iid": "<stable per-install UUID generated by the extension, stored in chrome.storage.local>",
  "agent_runtime": "browser_guard",
  "agent_runtime_version": "<browser family and major version, e.g. chrome-126 | edge-126 | firefox-128>",
  "aidr_version": "<extension version, e.g. 1.0.0>",
  "events": [
    {
      "event_id": "bg:<uuid>",
      "event_type": "privacy_scan",
      "timestamp": "<ISO-8601>",
      "site": "chatgpt|gemini|claude|copilot|perplexity|deepseek|mistral|grok|custom|other",   // custom = an administrator-configured internal AI site (managed customSites); never its host
      "action": "masked|blocked|warned|allowed",          // what the guard did to the outgoing prompt/paste/file
      "channel": "prompt|paste|file",
      "entity_counts": { "EMAIL": 2, "TC_KIMLIK": 1 },     // keys = privacy ENTITY_TYPES; integers 1..100000; max 32 keys
      "findings_count": 3,                                   // integer 0..1000000
      "policy_id": "<optional identifier matching ^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$>",
      "native_ner": "used|unavailable",                      // optional (additive): native NER outcome of the check; absent = NER off
      "reason": "paused",                                    // optional (additive): the user had paused protection (sent as in monitor mode); absent = not paused
      "policy_errors": 2                                     // optional (additive): integer 1..64, managed policy keys whose value was invalid and fell back to a fail-safe value; absent = none
    }
  ]
}
Rules: NO raw text, NO masked text, NO values, NO URLs beyond the site enum. Max 200 events per batch. Server maps action->decision for generic views: masked=>allow (redacted), warned=>ask, blocked=>deny, allowed=>allow.
`native_ner` (additive, status enum only): "used" = the native host's NER took part in the check; "unavailable" = NER was enabled or required (managed `requireNativeNer`) but gave no NER answer (host missing/crashed/timed out, rules-only host, malformed reply, text over the host limit). Under `requireNativeNer` such a check is `blocked` in enforcing modes and `allowed` + `native_ner: "unavailable"` in monitor mode; consumers must not count an "unavailable" check as clean. The extension rejects any other value. Server: the ingest projection (supabase/functions/ingest/events.ts `projectPrivacyEvent`) stores it in the event payload (`events.payload.native_ner`) when it is exactly "used" or "unavailable" and drops any other value (the event is still accepted, as if NER were off); no content is kept. The dashboard's recent privacy events mark an "unavailable" check as "not NER-checked". The requirement itself can come from the managed `requireNativeNer` key or from the tenant's dashboard setting, delivered as `browser_guard.require_native_ner` in the signed browser-guard-policy document (true wins).

`reason` and `policy_errors` (additive, counts and enums only): "paused" marks a send made while the user had paused protection (possible only where the managed policy sets `allowUserPause: true`; under any other managed policy pause is off), so it can be told apart from monitor-mode allowances. `policy_errors` counts the managed keys the extension found invalid (key names stay in the browser; "the whole policy was malformed or unreadable" counts as one); each such key runs at its fail-safe value (a list keeps its valid entries, other protection keys their strictest value). The extension rejects any other value. Server: the ingest projection stores `reason` when it is exactly "paused" and `policy_errors` when it is an integer 1..64 (`events.payload.reason` / `events.payload.policy_errors`) and drops anything else (the event is still accepted). An older server drops both fields and still accepts the event.

Shadow AI usage (only when the managed policy sets `shadowAi.mode` to `monitor` or `block-unsanctioned`), in the same envelope and batch:
    {
      "event_id": "bg:<uuid>",
      "event_type": "shadow_ai_usage",
      "timestamp": "<ISO-8601>",
      "service_id": "<catalog id, ^[a-z0-9][a-z0-9-]{0,31}$>",   // packages/browser-guard/src/sites/catalog.ts, e.g. chatgpt|poe|midjourney|otter
      "action": "visited|blocked",                                // a tab entered the service | the Shadow AI policy refused the navigation
      "count": 3,                                                 // integer 1..100000, aggregated since the previous flush (about one minute)
      "sanctioned": false,                                        // the service is in the policy's shadowAi.sanctioned list
      "policy_id": "<optional identifier, same syntax as above>"
    }
Rules: NO URL, host, path, query or page title: the only identifier is the catalog id (the extension never keeps the URL; it matches the host against the catalog and discards it). Unknown keys are dropped. The server rejects a missing/unknown action, a malformed service_id, a count outside 1..100000 or a non-boolean sanctioned (400 invalid_event), files a well-formed id it does not know yet under service_id "other", adds the catalog category (chat|coding|image|meeting|writing|search|agent|other) and maps action->decision: visited=>allow, blocked=>deny. An `ingest:browser_guard` key may send `privacy_scan`, `shadow_ai_usage` and `aup_acknowledgement` events only (see below).
Visibility needs host access: the extension counts visits and blocked attempts for a catalogued service only on origins the user granted from the options page (optional host permissions). The block itself needs no grant (a `declarativeNetRequest` block rule), so an ungranted origin is still blocked but contributes no count. It requests neither `tabs`, `webNavigation` nor `<all_urls>`. Dashboard aggregate: RPC `shadow_ai_summary(p_tenant_id, p_days 7|30)` (supabase/migrations/20260926000010_browser_shadow_ai_usage.sql), SECURITY INVOKER under the events RLS.
Acceptable-use acknowledgement (additive; only when the managed policy sets `acceptableUse` and telemetry is configured), in the same envelope and batch, at most one per install and notice version:
    {
      "event_id": "bg:<uuid>",
      "event_type": "aup_acknowledgement",
      "timestamp": "<ISO-8601>",
      "site": "chatgpt|gemini|claude|copilot|perplexity|deepseek|mistral|grok|other",   // where the user pressed "I understand"
      "notice_id": "<^[A-Za-z0-9][A-Za-z0-9._:-]{0,63}$, acceptableUse.id>",
      "notice_version": 3                                                               // integer 1..999999, acceptableUse.version
    }
Rules: NO notice title or text, NO user identity (the install is identified by the envelope iid only), NO URL. Unknown keys are dropped. The server rejects a missing/malformed or credential-shaped notice_id and a notice_version outside 1..999999 (400 invalid_event) and files an unknown site under "other". An `ingest:browser_guard` key may send `privacy_scan`, `shadow_ai_usage` and `aup_acknowledgement` events. The acknowledgement state itself stays in the browser (chrome.storage.local `aupAcknowledged`: notice id -> highest acknowledged version); an acknowledgement made while telemetry is not configured is not reported later. Dashboard aggregate: distinct installs per (notice_id, notice_version) in `governance_scorecard(p_tenant_id, p_days)` (supabase/migrations/20260927000060_governance_scorecard.sql), counts only.
Server response: existing ingest response shape (2xx with accepted count). Client retries with exponential backoff, keeps a bounded local queue (max 500 events), drops oldest on overflow, and never blocks the user's typing on telemetry.
Enrollment in the extension: options page (or managed policy keys controlPlaneUrl + apiKey) -> stored in chrome.storage.local; managed policy wins.
