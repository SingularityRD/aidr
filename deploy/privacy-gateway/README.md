# Privacy gateway (optional component)

The privacy gateway packages `aidr-privacy-service` from `packages/privacy` as an
optional, opt-in part of the standard self-hosted deployment: a Compose service
generated by `scripts/deployment-prepare.mjs --with-privacy-gateway`, or the
`privacyGateway.enabled` section of the Helm chart in `deploy/helm/aidr`.

## What it does

- Serves one listener, **only over mutual TLS**: every caller must present a
  client certificate issued by the configured client CA. The enforced egress
  path is `POST /v1/egress`, which also requires user, device and provider
  session tokens from the configured identity broker. The same listener serves
  the session routes (`/v1/session*`), `POST /v1/protect` (returns protected
  text to the caller, which then sends it itself: a helper, not an enforcement
  point) and the data-source/audio routes of `aidr-privacy-service`.
- Runs the privacy engine (rules plus the local NER model) on the request text,
  then sends the protected text to **one** configured provider destination
  (OpenAI Responses or Gemini generateContent) with a provider API key that only
  the gateway holds. Requests that the policy blocks never leave the gateway;
  requests that need review open a review case instead.
- Checks the provider's reply with the same policy and returns only the
  supported text output. It never forwards provider headers, cookies or raw JSON.
- Records each dispatch in a durable SQLite ledger and audit log on its state
  volume, so an interrupted send is reported as `unknown`, not retried silently.

## What it does not do

- **It is not a transparent proxy.** It does not intercept, decrypt or inspect
  network traffic that is not addressed to it. An agent, browser or SDK that
  calls a provider directly bypasses it entirely.
- It does not discover AI traffic on the network and it does not terminate TLS
  for provider domains.
- It does not give you a provider-compatible API: clients send AIDR's request
  shape (`requestId`, `destinationId`, `text`) and receive a receipt. Existing
  provider SDK calls must be changed to use it (see
  `packages/privacy/examples/platform/sdk-final-send.mjs`).
- It does not parse documents or images in this packaging: document parsing is
  not in the image, and `documents` in the service configuration is refused.

To make the gateway a control rather than an option, **you must also remove the
direct route**: block provider endpoints for clients with an egress firewall,
Kubernetes NetworkPolicy or an endpoint/MDM policy, and configure the clients
(SDK, MCP, browser extension) to use the gateway. Without that, the gateway only
protects the clients that choose to use it.

## Refusals (fail closed)

Preparation and rendering stop, and write nothing, when:

- mutual TLS material is missing, the server certificate is a CA, expired, not
  matched by its key, or uses a weak key (RSA < 2048), or the client CA is not a
  CA (`privacyGateway.mtls.enabled=false` is refused outright in Helm);
- the egress allow-list is missing, is a default route or a prefix shorter than
  /8 (IPv4) or /16 (IPv6), or names loopback, link-local (cloud metadata) or
  reserved ranges;
- the service configuration sets anything the deployment owns (`tls`, `host`,
  `port`, `secretStore`, `databasePath`, `documents`, `ner.python`), still holds
  a `REPLACE` placeholder, names a provider origin other than the two supported
  ones, or points trust files or the model manifest outside the mounted paths;
- (Compose) a referenced secret or trust file is missing, or the model manifest
  does not match the approved `ner.manifestSha256`.

The service itself also refuses to start without its mTLS material, its
approved model, its signed policy and a working identity broker.

## Image

`deploy/privacy-gateway/Dockerfile` is built from a staged context only
(`privacy-gateway.mjs` stages the compiled `dist/`, the offline NER worker and the
hash-pinned Linux wheel lock; no sources, tests or source maps):

- digest-pinned `node:24.21.0-bookworm-slim` and `python:3.11.15-slim-bookworm`
  bases (the Debian/glibc platform the Linux wheel lock was measured on);
- NER wheels installed with `--require-hashes`; an air-gapped build puts the
  wheels in the staged `wheelhouse/` and installs with `--no-index`;
- numeric non-root user `10001:10001`, application files root-owned and
  read-only, works with a read-only root filesystem (`/tmp` is the only scratch
  space; state, model, configuration and secrets are mounts);
- `HEALTHCHECK` that connects to the loopback listener. The listener opens only
  after the model, policy, broker and state are ready, so a TCP connect is the
  readiness signal; the probe holds no client certificate and sends nothing.

The image was defined and its build context tested; building it downloads the
pinned PyTorch/Transformers wheels and is a release-pipeline step.

### Container layout

| Path | Content | Source |
| --- | --- | --- |
| `/etc/aidr-privacy/config/service.json` | service configuration (references only) | prepared file / ConfigMap |
| `/etc/aidr-privacy/trust/` | IdP and broker CAs, broker client certificate, signed policy and keys | operator files / ConfigMap |
| `/etc/aidr-privacy/tls/server.pem`, `client-ca.pem` | server certificate and enrolled-client CA | operator files / TLS Secret |
| `/run/secrets/aidr-privacy/<ref>` | one file per secret reference, plus `aidr-privacy-tls-key` | Compose secrets / Secret volume |
| `/opt/aidr-models/` | approved NER model and manifest (read-only) | host directory / PVC |
| `/var/lib/aidr-privacy/` | durable control state | named volume / PVC |

The in-image configuration (`packages/privacy/deployment/container-service-config.mjs`)
reads secrets from mounted files because a container has no OS vault; the Linux
systemd units in `packages/privacy/deployment` keep using the OS vault.

## Compose (single host)

```bash
node scripts/deployment-prepare.mjs --mode self-hosted --output /srv/aidr ... \
  --with-privacy-gateway \
  --privacy-gateway-tls-cert-file server.pem --privacy-gateway-tls-key-file server.key \
  --privacy-gateway-client-ca-file enrolled-clients-ca.pem \
  --privacy-gateway-config-file service.json \
  --privacy-gateway-secrets-dir ./secrets --privacy-gateway-trust-dir ./trust \
  --privacy-gateway-models-dir /opt/aidr-models \
  --privacy-gateway-egress-cidrs 162.159.140.0/24,10.20.30.0/24 \
  [--privacy-gateway-dns-cidrs 10.0.0.53/32] [--privacy-gateway-subnet 172.31.253.0/28] \
  [--privacy-gateway-bind-address 10.0.0.5]
```

- `service.json` follows `packages/privacy/examples/platform/service-config.example.json`
  without the deployment-owned keys; trust paths sit under
  `/etc/aidr-privacy/trust/`, the model manifest under `/opt/aidr-models/`, and
  every `*Ref` names a file in `--privacy-gateway-secrets-dir`.
- The service `privacy-gateway` runs under the `privacy-gateway` Compose profile
  and is **not started** by `docker compose up`. It has its own bridge network
  (no route to the database or other AIDR services), publishes only the mTLS port
  (loopback unless `--privacy-gateway-bind-address` is set), and gets the CPU,
  memory and PID budget of the selected `--profile` from
  `deploy/onprem/resource-profile.json`.
- Secret files are written owner-only. Hand them to the container user, apply
  the egress firewall, then start the gateway:

```bash
sudo chown -R 10001:10001 /srv/aidr/privacy-gateway/secrets
sudo bash /srv/aidr/privacy-gateway/egress-firewall.sh
docker compose --project-directory /srv/aidr -f /srv/aidr/compose.yml --profile privacy-gateway up -d --build privacy-gateway
```

Docker does not filter container egress. `privacy-gateway/egress-firewall.sh`
adds `DOCKER-USER` rules that allow the gateway subnet to reach only the listed
CIDRs on TCP 443 (and DNS resolvers, when given) and reject everything else. It
is prepared, not applied: re-run it after every Docker or host firewall restart
(for example from a systemd unit ordered after `docker.service`). Re-running
is safe: the rules are built in the unused one of two chains
(`AIDR-PRIVACY-GW-A` / `AIDR-PRIVACY-GW-B`), completed with the final reject,
and only then swapped in at the top of `DOCKER-USER`; the previous chain is
removed after nothing jumps to it, so the subnet is never left unfiltered. If a
run fails before the swap, the previous rules stay in force. The single
`AIDR-PRIVACY-GATEWAY` chain of earlier releases is migrated the same way.
`deployment.json` records the mTLS fingerprints, destination and egress list.

## Kubernetes (Helm)

Create the inputs first; the chart never generates them:

- `privacyGateway.mtls.existingSecret`: `tls.crt`, `tls.key`, `ca.crt`;
- `privacyGateway.existingSecret`: one key per `*Ref` in `serviceConfig`;
- `privacyGateway.trustConfigMap`: one key per trust file, referenced as
  `/etc/aidr-privacy/trust/<key>`;
- `privacyGateway.models.existingClaim`: PVC with the approved model.

Then set `privacyGateway.enabled=true`, `privacyGateway.serviceConfig` and
`privacyGateway.egress.cidrs` (see `deploy/helm/aidr/ci/privacy-gateway-values.yaml`),
and build the image with
`node deploy/helm/build-images.mjs --only privacy-gateway --registry <registry> --build --push`.

The chart renders one replica (SQLite state), a pod that meets the `restricted`
Pod Security Standard (non-root 10001, read-only root, all capabilities dropped,
`RuntimeDefault` seccomp, no host access, no service-account token), secrets as
read-only files, TCP startup/readiness/liveness probes, and its own NetworkPolicy
(ingress 8443 from labelled pods and `clientCIDRs`; egress DNS plus TCP 443 to
`egress.cidrs`) even when `networkPolicy.enabled=false`. A `LoadBalancer` or
`NodePort` service requires `clientCIDRs` and keeps client addresses
(`externalTrafficPolicy: Local`).

NetworkPolicy is IP-based and provider addresses change. Pair it with an
FQDN-aware CNI policy or an SNI-filtering egress firewall, and restrict the
clients' own provider egress the same way.

## Status

This packages an existing service; it is not acceptance evidence. A real image
build, a qualified NER model, a live identity broker, customer client rollout and
egress enforcement on the customer's network remain open.
